# Архитектура и стиль кода SinglePipe

Документ фиксирует, **как устроены типы и исполнение в SinglePipe и почему**. Если новый код расходится с этими правилами, меняется либо код, либо документ, но осознанно и с записью причины.

Статусы решений:

- **Принято** — действует, новый код пишется так.
- **Цель** — направление согласовано, код ещё не написан или не переведён.
- **Открыто** — решения нет, варианты описаны.
- **Отклонено** — рассмотрено и не делаем; причины записаны, чтобы не обсуждать заново.
- **Отложено** — отдельный блок, направление согласовано, вернёмся позже (раздел 14).

Список задач и их статусы — в `tasks.md`. Замеры производительности — раздел 15 и `benchmarks/` в репозитории.

## 0. Структура пакета

Статус: **Принято.**

```
singlepipe/
├── __init__.py           # tasks, Task, ops; бэкенды не импортирует
├── tasks.py              # Task, встроенные задачи, get_task
├── ops.py                # операции-клей: crops (раздел 12.8)
├── _fanout.py            # ядро fan-out для .map (12.8)
├── adapters/
│   ├── base.py           # Adapter: async, поток модели, батчинг, map, close
│   └── hf_adapter.py     # HFAdapter (дальше torch, sklearn…)
└── schemas/
    ├── contract.py       # InputSchema, OutputSchema, ensure_implements
    ├── primitives.py     # BBox, Prediction, Detection
    ├── containers.py     # PredictionList
    ├── modalities/       # значения-модальности: Image (дальше Audio, Video…)
    └── image/            # схемы картиночных задач
        ├── base.py       # ImageTaskInput
        ├── classification.py
        └── detection.py
```

*Цель:* `singlepipe/graph/` (раздел 12). `ops.py` станет пакетом, когда функций станет много; `sp.ops.crops` от этого не изменится.

`tests/` повторяет структуру пакета. `benchmarks/` — скрипты замеров и их сырые выводы (раздел 15), в пакет не входит.

## 1. Три вида объектов

Любой класс в библиотеке относится к одному из трёх видов. От вида зависит, от чего наследоваться.

| Вид | Что это | Примеры | Основа |
|---|---|---|---|
| **Запись** | Данные с полями: валидируются, сериализуются, отдаются в FastAPI | `BBox`, `Prediction`, `Detection`, схемы задач | `pydantic.BaseModel` |
| **Значение или контейнер** | Объект со своим поведением, которому от pydantic нужно только одно: лежать в поле модели и валидироваться | `Image`, `PredictionList[T]` | Обычный класс + `__get_pydantic_core_schema__` |
| **Контракт** | Что адаптер требует от схемы задачи | `InputSchema`, `OutputSchema` | `BaseModel` + `abc.ABC` |

**Вопрос-проверка:** «является ли это *записью данных*?» Если да — `BaseModel`. Если это *значение* (картинка, коллекция), то наследование от `BaseModel` принесёт чужой интерфейс (`model_dump`, `copy`, `json`, свой `__iter__`), который будет мешать.

Статус: **Принято.**

### 1.1. Записи — `BaseModel`

- Предсказания и их части неизменяемы: `model_config = ConfigDict(frozen=True)`.
- Методы, которые «меняют» объект, возвращают новый через `type(self)(...)` и аннотируются `-> Self`. Так наследники сохраняют свой тип.
  - Исключение — чистый сдвиг всех координат (`Image.to_frame`): `box.model_copy(update=...)` сохраняет тип и **все поля** наследника. `model_copy` не валидирует, поэтому годится только там, где инварианты сохраняются по построению (сдвиг на одно целое). Там, где координаты меняются по-разному (`clip`, `scale`), — только конструктор с валидацией.
- Поведения в записях минимум: геометрия у `BBox` уместна, логика коллекций — нет (см. 1.2).

### 1.2. Значения и контейнеры — обычный класс

Механизм pydantic v2 для собственных типов — классметод `__get_pydantic_core_schema__`. Класс описывает, как себя валидировать и сериализовать, и после этого используется как тип поля.

Правила:

- Неизменяемость вручную: `__slots__`, без сеттеров; `__eq__`/`__hash__` — если нужны.
- Готовый экземпляр своего типа валидатор пропускает без копирования (`Image`, `PredictionList`). На этом держится передача значений между узлами графа без лишней работы.
- Сериализатор и JSON-схему (для FastAPI) класс определяет сам. `Image` в JSON пишет только размер, а JSON-схема — строка (URL, путь, data URI).
- Ошибка входа — `ValueError` (раздел 5).

**Коллекции** наследуют `collections.abc.Sequence`: реализуются `__getitem__` и `__len__`, а `__iter__`, `__contains__`, `__reversed__`, `index`, `count` приходят бесплатно.

Итерация, `len`, `in`, индексация, `top`, фильтры — поведение **контейнера** (`out.predictions.top(3)`), а не записи-выхода (`out`).

### 1.3. `Image`

Статус: **Принято.** `schemas/modalities/image.py`.

**Нормализация никогда не угадывает молча.** Любой источник приводится к RGB `PIL.Image`; всё, что дало бы неверную картинку без ошибки, — `ValueError`:

- массив пикселей — только `uint8` или float в `[0, 1]`. Float в `0..255` (после cv2) раньше становился белым, `int16` и `uint16` переполнялись по модулю, NaN становился нулём. Теперь это ошибка с подсказкой, как привести;
- NaN, бесконечность, пустой массив — ошибка;
- `bfloat16`-тензор переводится во float32 (в numpy нет bf16), дальше те же правила;
- `DecompressionBombError` (картинка больше `2 × PIL.Image.MAX_IMAGE_PIXELS`) — не `OSError`, ловится отдельно и становится `ValueError`;
- битый base64 в data URI — `ValueError` с указанием на data URI.

**EXIF-ориентация применяется** ко всем источникам, включая PIL-картинку пользователя (его объект не меняется). Так же делает HF `load_image` (проверено по исходникам transformers 5.19). Без этого фото с телефона доходит до модели боком, а коробки оказываются в другой системе координат, чем картинка у пользователя.

**Что живёт в `Image`, а что нет:**

| Уровень | Что | Примеры |
|---|---|---|
| Метод `Image` | «картинка → картинка», нужна только геометрия | `crop` |
| Функция `sp.ops` | смешивает картинку с предсказаниями или другими типами | `blur(image, dets)`, `reading_order(dets)` |
| Через `.pil` / numpy | всё остальное, API PIL не повторяем | поворот, контраст, фильтры |

Геометрия коробок — методы `BBox` (`clip`, `iou`, `scale`), а не `Image`.

**Загрузчики — функции и один диспетчер (`_to_pil`), не примеси.** Формат входа — способ создания объекта, а не его возможность: после конструктора все `Image` одинаковы, комбинировать нечего. `singledispatch` не подходит: путь, URL и data URI — все `str`, а регистрация `torch.Tensor` потребовала бы импорта torch. Вынести загрузчики в отдельный модуль — когда `Audio` понадобится общий «путь / URL / bytes → байты».

**Кроп помнит, откуда вырезан.**

- `crop(box) -> Self`: коробка режется по картинке (`clip`), затем расширяется **наружу** до целых пикселей (floor для левого и верхнего края, ceil для правого и нижнего), чтобы не терять край объекта. PIL сам округлял бы каждую координату, а за краем дополнял бы чёрным — ни того, ни другого. Ничего не осталось внутри картинки → `ValueError`.
- `origin: tuple[int, int]` — левый верхний угол в исходном кадре; у обычной картинки `(0, 0)`. Задаётся только `crop` (публичного аргумента нет — иначе это способ соврать про координаты); кроп кропа складывает смещения; `Image(crop)` и pydantic-поле сохраняют `origin`; в JSON не пишется.
- `to_frame(box)` сдвигает коробку на `origin` — сразу в исходный кадр, тип коробки сохраняется, обрезки нет.
- **Почему смещение хранится, а не вычисляется по коробке:** вырезанная область отличается от запрошенной коробки на округление и обрезку по краю. Перевод по исходной коробке сдвинул бы результат каскада (номер в кропе машины) на эти пиксели.
- `repr` показывает `origin`, если он не `(0, 0)`.

## 2. Контракт схем задач

Статус: **Принято.** Реализован в `schemas/contract.py`; классификация и детекция на нём.

| Класс | Члены |
|---|---|
| `InputSchema[T_co]` | абстрактные `from_raw(cls, raw: object) -> Self` и `to_pipeline_input(self) -> T_co`; свойство `output_context -> Mapping[str, Any]`, по умолчанию `{}` |
| `OutputSchema` | абстрактный `from_pipeline_output(cls, raw: Any, **context: Any) -> Self` |
| `ensure_implements(schema, contract)` | проверка при создании `Task` (раздел 12.6): передан класс, он наследует контракт, абстрактных методов не осталось; иначе `TypeError` с объяснением |

Решения:

- **Контракт наследует `BaseModel` и `abc.ABC`.** Библиотека всегда валидирует данные, поэтому схема без pydantic невозможна, а пользователь наследует одну базу: `class MyInput(InputSchema[str])`. Плата: схему на dataclass или attrs сделать нельзя.
- **Пользовательская схема обязана наследоваться от контракта**, как `nn.Module` в PyTorch или `BaseEstimator` в scikit-learn.
- **Проверка `inspect.isabstract` при создании задачи обязательна.** `@abstractmethod` запрещает только создание объекта; забытый абстрактный *классметод* (`from_raw`) при вызове молча вернёт `None`.
- **`output_context` не абстрактный**, по умолчанию пустой.
- **`__subclasshook__` и виртуальные подклассы не используем.**
- **Схемы поштучные.** Батч собирает адаптер (раздел 12.4); контракт схем от батчинга не меняется.
- **Поля схем — это порты узла графа.** `InputSchema` описывает, что узел читает, `OutputSchema` — что пишет (раздел 12.1).
- **`Any` только на границах с нетипизированным кодом:** сырой ответ бэкенда в `from_pipeline_output` и значения `output_context` (кандидат на `TypedDict` по задачам).

### 2.1. `ImageTaskInput`

Статус: **Принято.** `schemas/image/base.py`.

Общий вход задач с одной картинкой: поле `image: Image`, `from_raw` (готовый экземпляр своего класса проходит как есть, остальное — `model_validate({"image": raw})`, словарь не распаковывается), `to_pipeline_input` → RGB `PIL.Image`. Наследник добавляет только своё (детекция — `output_context` с размерами картинки).

**Сырой вход понимает только схема.** Адаптер вызывает `input_schema.from_raw(raw)` и больше ничего: своих веток для словаря или готовой схемы у него нет. Иначе вход интерпретировали бы два места по-разному.

### 2.2. Вариантность

Правило: **отдаёшь — ковариантно, принимаешь — контравариантно, и то и другое — инвариантно.**

- **`T_co` в `InputSchema` ковариантен**: `InputSchema[Cat]` подходит туда, где ждут `InputSchema[Animal]`.
- **Переопределение подчиняется принципу Лисков:** `from_raw(raw: object)` нельзя сузить до `raw: str`.
- **Только для чтения — абстрактные типы коллекций:** `Mapping` вместо `dict`, `Sequence` вместо `list`.
- **`PredictionList[T_co]` — ковариантный `Sequence`**: одна функция для `PredictionList[Prediction]` принимает предсказания любой задачи.
- **`Callable[[T], bool]` контравариантен по аргументам:** предикат для любого `Prediction` годится для фильтра детекций.

## 3. Сосуществование с pydantic

Статус: **Принято.**

**Нельзя определять в наследниках `BaseModel`:**

- dunder-методы: `__iter__`, `__eq__`, `__hash__`, `__getattr__`, `__copy__`;
- публичные имена: всё с префиксом `model_*`, а также наследие pydantic v1: `copy`, `dict`, `json`, `schema`, `schema_json`, `validate`, `construct`, `parse_obj`, `parse_raw`, `parse_file`, `from_orm`, `update_forward_refs`.

**Страховка:** тест, который падает, если наш атрибут перекрывает атрибут `BaseModel`. *Цель.*

## 4. Примеси

Статус: **Принято** как правило; сейчас не применяются.

Примесь уместна, когда возможности **комбинируются**: у одних задач есть, у других нет. Правила: без полей и состояния; в списке баз перед `BaseModel`; только через публичные атрибуты хозяина; подпадают под запрет имён из раздела 3.

## 5. Ошибки

Статус: **Принято.**

- Любой некорректный вход → `pydantic.ValidationError`.
- Внутри валидаторов бросаем **`ValueError`**, не `TypeError`: pydantic оборачивает только `ValueError` и `AssertionError`.
- Ошибки PIL и файловой системы (`OSError`, а также `DecompressionBombError`, который не `OSError`) превращаются в `ValueError` с указанием источника.
- Данные, которые дали бы неверный результат без ошибки, — тоже `ValueError`, а не тихое приведение (пиксели `Image`, раздел 1.3).
- Сетевые и HTTP-ошибки при загрузке URL остаются исключениями `httpx`.
- Ошибка программиста (не тот класс в `Task`) → `TypeError`.
- Ошибка конфигурации (неизвестное имя задачи, неизвестный HF pipeline) → `ValueError`, **до загрузки модели**, с подсказкой, что делать.
- *Цель:* ошибка внутри графа несёт имя узла и номер элемента при fan-out (раздел 12.2).

## 6. Предсказания

Статус: **Принято.**

- **Иерархия:** база `Prediction` (`label`, `score`, `label_id`); `Detection(Prediction)` + `box: BBox`. Отдельного `Classification` нет: пустой наследник был бы вторым именем для `Prediction`. Общая логика — один раз в `PredictionList[T_co]`. Наследник вроде `DetectionList` заводится, только когда появляется операция, которой нужны коробки (`clip`, `nms`).
- **`score` — вероятность в [0, 1]**, а не логит. Бэкенд, который выдаёт логиты, нормализует их сам.
- **`score` опционален везде.** `score=None` означает «бэкенд не дал уверенности». `top`, `top1`, `filter_by_score` падают с `ValueError`, если хотя бы у одного предсказания скора нет.
- **Сортировка стабильна.**
- **Строка в `filter_by_label` — одна метка.**
- **`BBox` может выходить за картинку с любой стороны, отрицательные координаты разрешены.** Детекторы, предсказывающие центр и размер (DETR, YOLO, RT-DETR), оценивают объект у края целиком, включая часть за кадром: `xmin = (cx − w/2)·W < 0`. Раньше было `ge=0`, и такая коробка роняла **весь** выход картинки, а коробка за правым краем проходила — асимметрия. Ограничение снято; координаты обязаны быть конечными (`allow_inf_nan=False`: `ge=0` попутно отсекал NaN, без него NaN прошёл бы и проверку `xmin < xmax`).
- **`BBox.clip`** режет все четыре стороны по `[0, W] × [0, H]` и возвращает `None`, если от коробки внутри картинки ничего не осталось. Это и есть фильтр «коробка — мусор»: ему нужен размер картинки, поэтому он не валидатор.
- **`BBox.scale(factor)`** — масштаб относительно центра: `scale(1.2)` отодвигает каждый край на 10% своей стороны. Множитель, а не процент: читается однозначно, `scale(1)` — без изменений. Отдельного `expand(ratio)` нет: это то же самое под другим именем. Результат может выйти за кадр; «у края стоп, с другой стороны рост» получается через `clip`/`crop`. `factor` — положительный и конечный, иначе `ValueError`.
- **Имя для пересчёта координат под картинку другого размера — не `scale`** (в CV `scale_boxes` значит именно это). Если понадобится — например `resize_frame`.
- **Схема детекции коробки не обрезает и не отвергает.** Выход — то, что дал бэкенд, включая коробки за краем с любой стороны. Обрезка меняет данные и может выкинуть коробку (а для трекинга важно, что объект уходит за кадр), поэтому это решение пользователя (`clip`, `crop`). Зафиксировано тестом.
- **Пустой список предсказаний по умолчанию** у всех выходов (`ImageClassificationOutput()`, `ObjectDetectionOutput()`).

## 7. Когда выносить общее

Статус: **Принято.**

- Выносим только то, что **уже одинаково** минимум в двух реальных задачах (или в двух адаптерах).
- Базовым классам — конкретные имена по смыслу (`ImageTaskInput`, `PredictionList[T]`), а не `BaseInput` «для всех 30 задач».
- Заглушки задач не держим: реализованная задача — это объект `Task`, планы — `tasks.md`. Списка имён «на будущее» в коде нет (раздел 12.6).

## 8. Сериализация

Статус: **Принято — отложено.**

Внутри одного процесса объекты между узлами графа не копируются, передаются ссылки. Своя сериализация понадобится на границе процессов или машин (исполнитель-процесс, remote-бэкенды, узел как endpoint — раздел 14) и для кэша. До тех пор хватает `model_dump`/`model_dump_json`.

## 9. Тесты

Статус: **Принято.**

- Структура `tests/` повторяет структуру пакета. Имена тестовых модулей уникальны по всему дереву.
- **Юнит-тесты** — без моделей, файлов и сети.
- **Интеграционные** — `tests/integration/`. Крошечная модель со случайными весами собирается в тесте; настоящие предобученные модели — `@pytest.mark.slow`.
- **Async-тесты** — через плагин `anyio` (в группе `dev` явно).
- **Конкурентность и батчинг — без замеров времени.** Модель удерживается на `threading.Event`/`Barrier` с таймаутом; неправильная реализация даёт неверные размеры пачек или понятный `TimeoutError`, а не флейк. Скорость меряется отдельно, в `benchmarks/` (раздел 15), а не в тестах.
- **Проверка самих тестов:** для нового механизма — нарочно сломать реализацию и убедиться, что тесты падают.
- **Импорт пакета** проверяется в отдельном интерпретаторе: в процессе pytest бэкенды уже загружены другими тестами.
- **Сначала тесты, потом рефакторинг.** Перенос в базовые классы не меняет тесты; осознанная смена API (как «коллекции у контейнера») — меняет, и это отмечается в коммите.
- Известный баг — `@pytest.mark.xfail(strict=True, reason=...)`.
- Тест проверяет поведение, а не устройство.

## 10. Стиль кода

Статус: **Принято.**

- Докстринги на английском. У модуля — docstring с объяснением «почему».
- `from __future__ import annotations`.
- Разделы внутри модуля — комментарии-линейки `# ---------------- раздел`.
- Тесты сгруппированы в классы `TestX`; параметры — `pytest.param(..., id=...)`; у неочевидного теста — docstring с причиной.
- `from_raw` строит схему через `cls.model_validate({...})`.

## 12. Исполнение: адаптеры, async, батчинг, граф

Статус раздела: **Цель**, кроме отмеченного «Принято» и «Открыто».

Сценарии, на которых проверялся дизайн: «полка» (детекция → кропы → классификация каждого), номера машин (каскад детекторов), документ → OCR → поля, модерация (независимые ветки), страховой случай (картинки + текст + документ → xgboost). Их целевой код — в `target_api_examples.py`.

### 12.1. Граф — это async-функция

```python
@sp.graph
async def shelf(image: Image) -> Counter[str]:
    dets = await detector(image)
    crops = sp.ops.crops(image, dets.predictions.filter_by_score(0.5), scale=1.1)
    results = await sku_classifier.map(crops)
    return Counter(r.predictions.top1.label for r in results if r.predictions.top1)
```

- **Связи — передача переменных.** Никаких `.add(...)` и строковых ключей: mypy проверяет связи, потому что это настоящие вызовы Python.
- **Порты — поля схем:** `dets.predictions` — это выходной порт детектора.
- **Граф внутри графа — просто вызов.**
- **Функции-клей — обычные функции.** `@sp.node` необязателен: добавляет функцию в протокол прогона и валидирует входы и выходы по аннотациям. Валидация на границах — всегда: по замеру она стоит 0–0,7 мс на вызов (раздел 15.2).
- **Ветки** — `asyncio.TaskGroup` (Python 3.11+).
- **Исполнение «как есть» с записью**, а не трассировка: работает любой Python (`if`, `for`). Трассировка не нужна, потому что батчинг делается на уровне адаптеров (12.4).
- **FastAPI:** декоратор сохраняет сигнатуру (`functools.wraps`), поэтому граф регистрируется как endpoint одной строкой. Проверено: FastAPI видит модели запроса и ответа через обёртку.

**Явный DAG (узлы + рёбра как описание, а не функция) — Отклонено.** Цена — свой язык графов: `for`/`if` из сценариев (номер для каждой машины, «пропустить, если не нашёлся») превращаются в специальные узлы map, условий и пропусков — путь LCEL в LangChain или DAG в Airflow. Плюсы явного графа и чем они закрыты у функции:

| Плюс DAG | У графа-функции |
|---|---|
| Структура до запуска: прогреть модели, посчитать память GPU, разложить по устройствам | Адаптеры создаются до прогона (модуль, `lifespan`); список моделей известен, неизвестно только, какие вызовутся |
| Конвейер на потоке (кадр n+1 в детекторе, пока кадр n в классификаторе) | Одновременные прогоны графа: у каждого адаптера свой поток и очередь (12.4) |
| Перезапуск с середины, кэш по узлам (Dagster, Hamilton) | Протокол прогона (12.2) + кэш для разработки (13) |
| Граф как артефакт: сериализовать, версионировать, отправить исполнителю | Граф — код, его версионирует git; удалённое исполнение графов — ниша Ray |
| Надёжное исполнение: повтор узла, продолжение после падения (Airflow, Temporal) | Прогон инференса — миллисекунды–секунды, проще повторить целиком; повтор сетевого вызова — внутри адаптера (`RemoteAdapter`) |

Сборка пайплайна без кода и визуальный редактор — не цель библиотеки. Единственное, чего у функции нет совсем, — граф как артефакт, и он не нужен. Распределённость узлов решается не структурой графа, а тем, где живёт узел (раздел 14).

### 12.2. Протокол прогона

- Каждый вызов узла записывается: имя, вход, выход, время. Хранится всё (для отладки и настройки); режим «только итог» — когда упрёмся в память.
- Состояние только дополняется, ничего не перезаписывается.
- Протокол живёт в `contextvars`: контекст переходит в задачи `TaskGroup`, поэтому параллельные прогоны (50 запросов к FastAPI) не смешиваются.
- Ошибка несёт имя узла и номер элемента при fan-out: «узел `sku_classifier` [кроп 7 из 14]: …».

### 12.3. Async-ядро и вычисления вне event loop

- Вызов адаптера асинхронный: `await adapter(x)`.
- **Async — это оркестровка; вычисления идут в рабочем потоке модели**, вне event loop. Иначе один forward заморозит весь сервер. torch и C-код отпускают GIL.
- Синхронный фасад для скриптов (`run_sync`) — **Открыто**, не сейчас. В Jupyter `await` работает прямо в ячейке.
- **Реализовано в `Adapter` (`adapters/base.py`) — Принято.** `async def __call__(raw) -> OutT`:
  - `from_raw` — в общем пуле потоков loop'а (`asyncio.to_thread`): валидация может грузить URL и декодировать картинку, и не должна держать ни loop, ни модель;
  - провалидированный вход уходит в очередь своего рабочего потока адаптера (один поток на модель, назван по задаче), вызывающий ждёт `concurrent.futures.Future` через `asyncio.wrap_future`;
  - к event loop адаптер не привязан: очередь живёт в потоке, а не в loop'е, поэтому один адаптер обслуживает вызовы из любого loop'а (в тестах каждый тест — новый loop).
  - Два API (`predict` и `async __call__`) не делаем.
- **Почему не асинхронный `from_raw`:** валидаторы pydantic синхронные, `await` внутри них невозможен. Настоящая async-загрузка URL потребовала бы async-контракта и отдельного слоя загрузки до валидации. `to_thread` даёт тот же результат для loop'а без смены контракта; пересмотреть, если пул потоков станет узким местом.
- **Жизненный цикл — `close()`, Принято.** Досчитывает уже поставленные в очередь вызовы, останавливает поток, вызывает хук `release()` (отпустить модель); повторный вызов безопасен; вызов после закрытия → `RuntimeError`. Постановка в очередь и `close()` упорядочены блокировкой, иначе вызов мог бы проскочить после сигнала остановки и ждать вечно. Поток — демон: без `close()` он не держит интерпретатор. Контекстного менеджера нет: в графе и FastAPI адаптеры живут всё время процесса.
- Модель грузится синхронно в `__init__`, **до** `super().__init__()`: тот запускает поток, и неудачная загрузка не должна оставлять поток.

### 12.4. Батчинг

Статус: **Принято, реализовано в `Adapter`.** Динамический батчинг: пользователь пишет код по одному элементу, пачки собираются сами.

| Уровень | Пример | Механизм |
|---|---|---|
| Внутри одного вызова | `await classifier.map(crops)` | `map` запускает все вызовы сразу; одновременные вызовы собираются очередью адаптера |
| Табличка | xgboost на 10 000 строк | бэкенд батчевый по природе |
| Между прогонами графа | 50 запросов к FastAPI | та же очередь адаптера |

- **Очередь — в рабочем потоке модели.** Поток берёт первый вызов и добирает следующие, пока не наберёт `max_batch_size` или не истечёт `max_wait_ms` от первого; затем один `run_batch` на всю пачку, результаты — каждому ожидающему. Так работают Triton и `@serve.batch` в Ray Serve.
- **Пачки растут под нагрузкой сами:** вызовы, пришедшие, пока модель считает, попадают в следующую пачку даже при `max_wait_ms=0`. Без нагрузки задержка не добавляется. Подтверждено замером (15.3): при 64 клиентах и `max_wait_ms=0` средняя пачка 30 из 32.
- **По умолчанию `max_batch_size=1`, `max_wait_ms=0`** — поведение как без батчинга, пока пользователь не включит. Параметры именованные, одинаковые у всех адаптеров; неверные значения → `ValueError`.
- **Ошибки:**
  - плохой вход отсекается валидацией до очереди и в пачку не попадает;
  - упал `to_pipeline_input` у элемента — падает только он;
  - упал `run_batch` или вернул не то число выходов — падает вся пачка;
  - упал разбор выхода (`from_pipeline_output`) у элемента — падает только он.
  - Рабочий поток от исключения не умирает: иначе все следующие вызовы повисли бы.
- **Отменённый вызов** (таймаут, отмена задачи) выбрасывается из пачки до бэкенда.
- Схемы остаются поштучными; пачка существует только внутри `run_batch`. Склеивать входы в вход своего бэкенда — работа адаптера (список для HF pipeline, 2D-массив для sklearn, `stack` для torch).
- **HF:** пачка уходит как `pipeline(list, batch_size=n)`, один вход — как `pipeline(x)`. Проверено интеграционным тестом на крошечной ViT: один вызов pipeline на 4 картинки, метки и вероятности совпадают с поштучными до 1e-5.
- **Цена:** окно ожидания добавляет задержку каждому запросу ради пропускной способности; `max_batch_size` ограничивает память GPU; у текстов разной длины будет padding (решать с текстовыми задачами).
- **Замер (15.3): окно ожидания не окупается.** Совет для сервера — `max_batch_size=16–32, max_wait_ms=0`.

### 12.5. Устройство и исполнитель

- `device=` — единый параметр у всех адаптеров (`"cpu"`, `"cuda:0"`, `"auto"`).
- **Исполнитель** — отдельная сущность адаптера: «где и как считать». По умолчанию один поток на модель (это же правильно для памяти GPU и потокобезопасности HF pipeline). Позже за тем же интерфейсом: реплики на нескольких устройствах, пул процессов для CPU-моделей с тяжёлым Python-кодом (`spawn`, не `fork`).
- Несколько машин — не наша задача: это ниша Ray и Ray Serve.
- **Открыто:** память GPU при многих моделях (ленивая загрузка, выгрузка на CPU, fp16, квантизация). Сборка Python без GIL (3.14) может сделать поток на модель полноценным параллелизмом и для CPU — проверить готовность бэкендов.

### 12.6. Задача как объект `Task[In, Out]`

Статус: **Принято.** `singlepipe/tasks.py`, `adapters/hf_adapter.py`. Проверено в mypy `--strict` на настоящих схемах.

**Задача определяется входом и выходом.** `Task` связывает имя с двумя схемами и несёт их типы:

```python
@dataclass(frozen=True)
class Task(Generic[InT, OutT]):  # InT: InputSchema[Any], OutT: OutputSchema
    name: str
    input_schema: type[InT]
    output_schema: type[OutT]  # __post_init__: ensure_implements для обеих


image_classification = Task(
    "image-classification", ImageClassificationInput, ImageClassificationOutput
)
object_detection = Task("object-detection", ObjectDetectionInput, ObjectDetectionOutput)
```

- **Встроенные задачи — готовые объекты**, имён схем пользователь не пишет: `HFAdapter(model, sp.tasks.object_detection)`.
- **Своя задача — одна строка, один раз:** `is_cat = Task("is-cat", ImageTaskInput, IsCat)`, дальше передаётся как встроенная. Можно взять готовый вход и свой выход.
- **Схемы проверяются при создании задачи** (`ensure_implements` в `__post_init__`): перепутанные или чужие схемы падают сразу `TypeError`, и у тех, кто mypy не запускает.
- **`Task` — frozen dataclass**, не pydantic-модель: это описание, а не данные.
- **Имена объектов — snake_case** (`image_classification`): это экземпляры, не классы. Не называть объект так, чтобы он перекрыл встроенное имя (`object`); ruff ловит это правилом `A`.
- **Строка для конфигов и CLI — `get_task(name)`**: ищет только среди встроенных задач, неизвестное имя → `ValueError` со списком. Тип выхода по строке — `Task[Any, Any]`.
- **Реестра нет.** Объект задачи и есть связка «задача → схемы».

**Enum имён задач (`TaskType`) удалён.** Причины:

- связку «задача → схемы» несёт `Task`, enum остался бы только списком имён;
- 30 имён при одной-двух реализованных задачах — те же заглушки (раздел 7) и ловушки в автодополнении; `sp.tasks.` показывает ровно то, что работает;
- совпадение значений со строками HF теряет смысл для задач вне HF (OCR, табличка, свои задачи);
- планы живут в `tasks.md`.

**Имя задачи — только имя.** Чем считать задачу, решает адаптер. У встроенных HF-задач имя совпадает со строкой pipeline, и `HFAdapter` берёт его по умолчанию.

**`HFAdapter`:**

```python
HFAdapter(model, task, *, hf_task=None, device=None,
          max_batch_size=1, max_wait_ms=0, **pipeline_kwargs)
```

- `HFAdapter(Adapter[InT, OutT])`, два `@overload`: `Task[InT, OutT]` → точный тип выхода, `str` → `OutputSchema`. `await adapter(raw) -> OutT`, без `cast`.
- `hf_task` — строка HF pipeline; по умолчанию `task.name`. Нужна для своей задачи поверх HF-модели.
- Порядок в `__init__`: разрешить задачу → проверить имя pipeline по реестру HF (`PIPELINE_REGISTRY.check_task`, понимает алиасы и `translation_xx_to_yy`) → проверить torch → загрузить модель → `super().__init__()` (запуск потока).
- Схемы адаптера доступны как `adapter.task.input_schema` / `adapter.task.output_schema`.
- `pipeline_kwargs` доходят до `transformers.pipeline` без изменений: `dtype=torch.float16`, `image_processor=...` — проверено бенчмарком (15.1, 15.4).

### 12.7. Адаптеры: база, бэкенды, Connector

**База `Adapter` — Принято.** `adapters/base.py`, `Adapter(ABC, Generic[InT, OutT])`.

- В базе всё, что от бэкенда не зависит: `async __call__`, валидация вне loop'а, поток модели, очередь и батчинг (12.4), `output_context` каждого входа → его выход, `close()`, ошибки.
- **Бэкенд — один абстрактный метод `run_batch(inputs) -> outputs`:** входы бэкенда (`to_pipeline_input()` каждого) списком, сырые выходы той же длины и в том же порядке. Нарушение длины → `RuntimeError` с именем класса. Вызывается в рабочем потоке, может блокировать.
- **Необязательный хук `release()`** — отпустить модель; вызывается `close()` ровно один раз.
- **`run_batch` публичный: это точка расширения для пользователя.** Свой адаптер под любую библиотеку — подкласс: загрузить модель, `super().__init__(task, ...)`, реализовать `run_batch`. Тип выхода mypy выводит так же, как у `HFAdapter`.
- **Почему вынесено при одном бэкенде** (исключение из раздела 7): выносится не догадка об интерфейсе бэкендов, а механика, которая про HF не знает; интерфейс бэкенда — один метод, и он проверен на бумаге:
  - HF — `pipeline(list, batch_size=n)`;
  - torch — `transform` каждого → `stack` → `model(batch)` → softmax → по строкам;
  - sklearn / xgboost — `vstack` → `predict_proba` → по строкам;
  - адаптер над функцией — функция на пачку или цикл по элементам;
  - remote API — один запрос со списком или цикл запросов.
- **Открыто:** что не ложится в `run_batch` — потоковая генерация текста (выход по токенам) и бэкенды с несколькими входами на элемент. Решать с текстовыми задачами.

**Connector — Цель.**

- `Connector` выбирает адаптер по объекту модели: строка → HF, `nn.Module` → torch, объект с `predict` → sklearn. `backend=` перекрывает автоопределение.
- Connector не импортирует бэкенды: тип проверяется через `sys.modules`, иначе `import singlepipe` потребует torch.
- **Адаптер приводит выход своего бэкенда к формату схемы.** Для HF-задач формат совпадает с выходом pipeline (например `[{"label", "score"}]`); для задач вне HF «сырой выход» определяем мы, и каждый адаптер приводит к нему. Схемы о бэкендах не знают.

**Единые имена параметров — Принято.** Одно понятие — одно имя во всех адаптерах; понятие одного бэкенда называется по нему.

- Общие: `model` (первый позиционный), `task` (второй), `device=`, `max_batch_size=`, `max_wait_ms=`. Всё после `task` — только именованное (`*`).
- Своё у бэкенда: с префиксом или из его терминологии — `hf_task=` у HF, `labels=`/`transform=` у torch.
- Connector пробрасывает именованные параметры в выбранный адаптер; пользователь видит одну форму вызова.

**Узел как endpoint (`sp.serve`, `RemoteAdapter`)** — отдельный блок, раздел 14.

**Адаптер над функцией — Цель.** Пользователь даёт функцию «вход бэкенда → сырой выход», библиотека оборачивает её схемами задачи. Так любая библиотека (ultralytics, OCR-движки, свой код) работает с любой задачей без своего подкласса, и этим же подменяются модели в тестах. На базе `Adapter` это несколько строк: `run_batch` вызывает функцию. Естественное место — рядом с Connector.

**Бэкенды не тянутся без нужды — Принято, реализовано.**

- Ядро (`httpx`, `pillow`, `pydantic`, `numpy`) — всегда. Бэкенды — extras: `hf = transformers + torch`, `detr = hf + timm`, `torch`, `all`. Группа `dev` тянет `singlepipe[all]`.
- **`torch` входит в `hf`:** без него transformers не грузит модели. Нужна своя сборка под CUDA — torch ставится поверх.
- Бэкенд импортируется только в модуле своего адаптера. `singlepipe/__init__.py` экспортирует `tasks` и `Task`, но не адаптеры: `from singlepipe.adapters.hf_adapter import HFAdapter`. Пользователь в целевом API работает через Connector.
- `Image` распознаёт тензоры torch через `sys.modules`, не импортируя torch: тензор не может существовать без уже импортированного torch.
- Без бэкенда — понятная ошибка с командой установки: нет `transformers` → `ModuleNotFoundError` при импорте модуля адаптера; нет `torch` → `ImportError` до загрузки модели. Если `transformers` есть, но сломан, настоящая ошибка не подменяется.
- `import singlepipe`: 3,17 с → 0,20 с. Проверяется тестом в отдельном интерпретаторе.
- Порядок бэкендов: HF → torch → sklearn → remote/ONNX. TF — в конце: Keras 3 работает поверх torch и JAX.

### 12.8. Операции-клей

«Клей» — код между вызовами моделей: выход одной почти никогда не годится как вход следующей.

- Не строим свой язык обработки данных: всё специфичное пользователь пишет обычными функциями.
- Библиотека даёт частые операции, по мере появления в сценариях (раздел 7). Куда кладётся операция — по таблице из 1.3.
- **Принято, реализовано:** `Image.crop`, `Image.origin`, `Image.to_frame` (1.3); `BBox.scale`, `BBox.clip` с четырёх сторон (6); `sp.ops.crops` и `Adapter.map` (ниже). Плюс уже существовавшие `BBox.iou`, фильтры `PredictionList`.
- **Отказались:** `sp.ops.to_frame(box, origin=car.box)` — стал методом кропа, потому что смещение по исходной коробке неточно (1.3).

**`sp.ops.crops(image, boxes, *, scale=1.0) -> list[Image]` — Принято.** `singlepipe/ops.py`, первая функция `sp.ops`.

- По кропу на коробку, порядок как у `boxes`; принимает детекции и голые `BBox` (`PredictionList[Detection]` передаётся как есть). `scale` — один на все коробки, через `BBox.scale`.
- Сначала было отклонено как однострочник (`[image.crop(d.box) for d in dets]`); вернули, потому что операция встречается в трёх сценариях из пяти (полка, номера, документ) — правило раздела 7. Особое по коробкам (свой `scale`, условие) — по-прежнему list comprehension.
- Функция, а не метод `Image` или контейнера детекций: смешивает картинку с предсказаниями (таблица 1.3); `bottles.crops(image)` читается задом наперёд.
- Неверный `scale` проверяется сразу, даже при пустом списке; коробка вне картинки → `ValueError` с заметкой `crops: box at index i`.

**Fan-out — `Adapter.map(items, *, errors="raise")` — Принято.** `adapters/base.py`, ядро — `singlepipe/_fanout.py`.

- **Зачем, кроме краткости.** Цикл `await` отправляет вызовы по одному: очередь адаптера никогда не видит больше одного, и батчинг молча не работает. `asyncio.gather` при ошибке не отменяет остальные — модель досчитывает ненужное (проверено). `TaskGroup` отменяет, но бросает `ExceptionGroup`. `map` запускает всё сразу, отменяет остальные и бросает исходное исключение.
- **Ошибка — исходное исключение с заметкой** (`add_note`): `TenTimes(task='numbers').map: item at index 2 of 4`. Тип не меняется: `ValidationError` остаётся `ValueError`, обработчики FastAPI и `except` работают. Индекс с нуля, как в списке результатов. Своего класса ошибки нет.
- **Два режима, решает разработчик** (продолжать молча опасно: модерация пропустит контент, «полка» посчитает 13 вместо 14):
  - `errors="raise"` (по умолчанию) → `list[OutT]`; первая ошибка отменяет остальные и выходит наружу;
  - `errors="collect"` → `list[OutT | Exception]` той же длины и порядка; mypy заставляет обработать `Exception` (два `@overload` по `Literal`, проверено).
- Собирается только `Exception`; `CancelledError`, `KeyboardInterrupt` и прочие `BaseException` проходят насквозь. Закрытый адаптер → `RuntimeError` до отправки элементов; неизвестный `errors` → `ValueError`.
- **Общая ошибка пачки.** `_run` ставит один объект исключения всем вызовам упавшей пачки, поэтому заметка одна на исключение и перечисляет все индексы (`items at indices 0, 1, 2 of 3`), а не копится по штуке на элемент.
- **Ограничение:** если в `raise` падает вся пачка, поднимается тот её элемент, что проснулся первым; порядок в очереди зависит от того, чья валидация закончилась раньше, поэтому индекс в заметке может отличаться от прогона к прогону. Исключение то же.
- **Почему не `__call__` со списком.** Список бывает законным *одним* входом (строка признаков табличной модели, диалог для LLM); адаптер не знает, пачка это или элемент, и молча разрезал бы строку на вызовы по числу. Так устроен HF pipeline, и это известный источник путаницы. «Один или много» видно в коде.
- **Почему метод, а не `sp.each(node, items)`.** Метод виден в автодополнении и типизируется даром (`Adapter[InT, OutT]`). Отдельной публичной функции нет: один путь.
- **Цель — `.map` у любого узла.** Ядро написано для любой async-функции; `@sp.node` и `@sp.graph` получат `.map` на нём же. Общие аргументы — через `Concatenate[In, P]`: первый аргумент — элемент, остальные общие и типизируются (`read_plate.map(cars, frame=frame)`; mypy проверяет и элементы, и `frame` — проверено на прототипе). `functools.partial` не нужен.
- **Потом, по замеру:** ограничение одновременности (`max_concurrency`) для тысяч элементов; положить все входы в очередь разом без задачи на элемент (метод видит очередь, внешняя функция — нет). Замер 15.2: пачки `map` неполные (21,3 из 32) — довод за второе.

- **Кандидаты, когда появятся сценарии:** `BBox.pad(pixels)` — ровный отступ, нужен OCR номеров (у коробки 5:1 `scale` добавляет по ширине в 5 раз больше, чем по высоте); `sp.ops.reading_order`, `sp.ops.blur`, `sp.ops.score_of`.

## 13. Открытые вопросы

- **Быстрый путь HF без механики pipeline** — ×1,76–2,28 на классификации; варианты и условия — раздел 15.4.
- **Цена повторной нормализации `Image` и неполные пачки `map`** — 2–9% против ручного батчинга, Отложено до 15.4 (раздел 15.2).
- **Что не ложится в `run_batch`** (потоковая генерация, несколько входов на элемент) — раздел 12.7.
- **Кэш.** Отложен до графа с несколькими моделями. Три разных вещи:
  - одна модель на процесс для нескольких адаптеров (память GPU, 12.5);
  - кэш результатов — обёртка после валидации и до очереди, только для детерминированных задач, ключ включает версию модели; попаданий в инференсе мало, вопросы приватности;
  - **кэш для разработки** (дисковый, по ключу «модель + вход») рядом с протоколом прогона: перезапуск графа после правки клея без пересчёта моделей. Самый ранний кандидат.
  - Мелочь: кэш загрузок по URL.
- **`label_id`.** Поле есть, адаптер его не заполняет. Источник — `pipe.model.config.label2id`. Тест `test_label_id_is_not_filled_yet` фиксирует текущее поведение.
- **`Image` в выходе графа через FastAPI.** В JSON уходит только размер. Если нужна сама картинка (например размытая при модерации) — отдельное решение: data URI, ссылка на хранилище или отдельный endpoint.
- **Синхронный фасад** — раздел 12.3.
- **Память GPU** — раздел 12.5.
- **Имя `PredictionList`** — «пока так», переименовать, если найдётся лучше.
- **Интеграционный тест детекции** на крошечной DETR, по образцу классификации.
- **mypy `strict = false`** в проекте; код пишется и проверяется под `--strict`. Включить `strict` в `pyproject.toml` — отдельное решение.
- **Недоверенный вход в FastAPI.** README показывает `classify(url: str)`, а строка из запроса для `Image` может быть:
  - локальным путём — сервер прочитает любой файл, а по тексту ошибки можно проверять существование путей;
  - произвольным URL — запросы во внутреннюю сеть (SSRF);
  - большим ответом — лимита на размер скачивания нет (защита от бомбы срабатывает только при декодировании).
  Вариант: режим «недоверенный вход» — только data URI и URL из allowlist, лимит размера. Решить до того, как продвигать FastAPI-сценарий.
- **Один плохой элемент выхода роняет весь выход.** Коробка нулевой ширины (`xmin == xmax`) — например после `int()` в HF-пайплайне у крошечного объекта — даёт `ValidationError` для всей картинки. Варианты: отбрасывать такие элементы с предупреждением или ошибка по элементу. По тем же правилам, что у `map`: не продолжать молча — битый элемент в явное поле ошибок, а не тихо выкинуть.
- **Наследники `BBox` с обязательными полями.** `clip` и `scale` строят результат через `type(self)(xmin=..., ...)` и на таком наследнике падают: поле не передано. Если такие наследники понадобятся — `self.model_validate(self.model_dump() | {координаты})` (все поля и валидация). Пока не нужно.

Закрыто:

- *Python 3.11 и стабы numpy* — решено подъёмом `requires-python` до `>=3.12` (mypy `python_version = 3.12`).
- *`torch` в extra `hf`* — да (12.7).
- *Цена проверки типов на границах узлов* — 0–0,7 мс на вызов, проверяем всегда (15.2).

## 14. Распределённое исполнение

Статус раздела: **Отложено.** Отдельный блок: возвращаемся к нему после графа (12.1–12.2). Ниже — согласованное направление, чтобы не обсуждать заново, и предварительные задачи, которые нужны и другим блокам.

### 14.1. Узел как endpoint — Цель

Каждая модель может жить отдельным сервисом, а граф-функция при этом не меняется: где живёт узел, решается при развёртывании.

```python
app = sp.serve(HFAdapter("facebook/detr-resnet-50", sp.tasks.object_detection))  # на gpu-1
detector = sp.RemoteAdapter("http://gpu-1:8000", sp.tasks.object_detection)       # в графе
```

- `RemoteAdapter(url, task, ...)` — обычный адаптер, как `HFAdapter`: та же база `Adapter`, те же `Task[In, Out]` и типы для mypy, только `run_batch` — HTTP-запрос. Перенести узел на другую машину — поменять одну строку при создании адаптера.
- `sp.serve(adapter)` — тонкая обёртка: FastAPI-приложение или роутер, схемы и Swagger — из `adapter.task`. Развёртывание (Docker, k8s, автомасштабирование) — не наше, иначе это своя serving-платформа (BentoML, Ray Serve). Наше отличие — один типизированный `Task` на обоих концах и неизменный код графа.
- Зачем: независимое масштабирование; одна модель в памяти GPU на много клиентов; изоляция зависимостей (разные версии torch); клиенты на других языках.
- Решения, когда дойдём:
  - **сервер отдаёт готовую схему выхода**, а не сырой ответ бэкенда: клиент не привязан к бэкенду сервера. Нужен переопределяемый хук разбора выхода в `Adapter` (сейчас база всегда зовёт `from_pipeline_output`);
  - endpoint принимает **список** входов: клиент собирает пачку в один запрос, сервер — пачки из запросов разных клиентов;
  - картинки по умолчанию **без потерь** (PNG/WebP): JPEG меняет пиксели, и удалённая модель ответила бы не так, как локальная;
  - `origin` по сети не ходит: клиент держит свой `Image`, коробки в ответе — в координатах присланной картинки, `to_frame` работает у клиента;
  - ошибки по элементам в ответе, иначе одна плохая картинка роняет пачку чужого клиента; плохой вход → 422 → `ValueError` у клиента; сеть → `httpx`, таймауты и повторы — параметры `RemoteAdapter`;
  - `GET /info` — задача, схемы, версия модели; `RemoteAdapter` проверяет совместимость в `__init__`.
- Граф тоже можно выставить сервисом (12.1), тогда другой граф вызывает его как узел.
- Несколько копий узла — балансировщик перед ними, это инфраструктура; `RemoteAdapter` знает один адрес.

### 14.2. Слои — подграф как сервис — Цель

Данные в схеме «звезда» идут через процесс графа: каждая картинка и каждый кроп — по сети туда и обратно. Узлы, которые обмениваются тяжёлыми данными, объединяются в один сервис:

```
сервис «полка» (одна машина):   детектор → кропы → классификатор     данные не выходят из машины
сервис «номера» (другая):       машины → номера → OCR
главный граф:                   await shelf(img), await plates(img)  по сети — картинка и итог
```

Слой независимо разворачивается, масштабируется и обновляется; внутри — без сети, снаружи — обычный узел. Работает на текущем дизайне без нового механизма.

### 14.3. Передача ссылок вместо данных — Открыто, после замеров

Классификатору нужна не копия кропа, а картинка и область. Кроп уже знает, откуда вырезан (`origin`), поэтому по сети можно слать «картинка `sha256:…` + область» (16 байт), а пиксели — один раз на сервер. Адресация по содержимому: клиент спрашивает, есть ли у сервера картинка с таким хешем; нет — загружает; сервер держит кэш по хешу. Общее хранилище не обязательно (если есть — ссылкой может быть URL в нём). Делать только после `serve`/`RemoteAdapter` и замеров трафика (раздел 7 и принцип «не оптимизируем заранее»).

### 14.4. Прямая передача узел → узел — Отклонено

Узлы отправляют результаты друг другу (очереди между слоями), граф в центре не нужен. Отклонено: логика между слоями (кропы, фильтры, `if`, «пропустить, если не нашлось») переезжает внутрь узлов, граф размазывается по серверам, ошибки с номером элемента и протокол прогона требуют распределённой трассировки. По сути это явный DAG (12.1, отклонён), только распределённый, — ниша Ray и потоковых платформ. Слои получаются проще через 14.2.

### 14.5. Предварительные задачи — общие с другими блоками

Блок отложен, но эти задачи нужны и без него — их делаем в рамках других блоков:

| Задача | Где нужна кроме 14 |
|---|---|
| **Недоверенный вход `Image`**: только data URI / байты / URL из allowlist, лимит размера | FastAPI-сценарий из README уже сейчас; граф как endpoint (12.1) |
| **Сериализация пикселей `Image`** (data URI или бинарное тело, без потерь) | `Image` в выходе графа через FastAPI (13); дисковый кэш для разработки (13) |
| **Схемы выхода без потерь через JSON** (`model_dump_json` → `model_validate_json`), тест на каждую задачу | ответы FastAPI; кэш для разработки |
| **Политика ошибок по элементу** | решена для `map` (12.8); осталось «один плохой элемент роняет весь выход» (13) |
| **Хеш содержимого `Image`** | ключ кэша для разработки (13); ссылки 14.3 |

## 15. Производительность: замеры

Статус раздела: **Принято** (выводы 15.2–15.3), **Открыто** (15.4). Скрипты, методика и сырые выводы — `benchmarks/` в репозитории (`README.md`, `results/`).

### 15.1. Методика

- Kaggle, одна Tesla T4 из двух, 4 vCPU; Python 3.13.16, torch 2.11.0+cu130, transformers 5.20.2, singlepipe 0.2.0. Модель `google/vit-base-patch16-224`, одна картинка COCO `000000039769.jpg` (640×480), декодирована до замера (кроме строки `adapter(path)`).
- Прогрев перед каждым замером; медиана и p95; пропускная способность — картинок в секунду. Реальный размер пачки записывает наследник `HFAdapter` (`run_batch` считает `len(inputs)`).
- **Сравниваются только прогоны одной сессии.** Один и тот же fp32-прогон в разных сессиях Kaggle: 60,4 и 49,5 img/s (−18%). Эталон и вариант — подряд, в одной сессии.
- `bench.py` передаёт одни и те же настройки (`--dtype`, `--backend`) эталонному pipeline и каждому адаптеру через `HFAdapter(**pipeline_kwargs)` и останавливается, если у адаптера они другие.
- **transformers 5:** `ViTImageProcessor` — бэкенд torchvision (по умолчанию), `ViTImageProcessorPil` — PIL. `use_fast` устарел → `backend="torchvision" | "pil"`. По имени класса бэкенд не определить — проверять `processor.backend` (на этом я ошибся: принял `ViTImageProcessor` за PIL).

### 15.2. Цена типизированной границы — Принято

| fp16, T4 | эталон | адаптер |
|---|---|---|
| один вызов, медиана | `pipeline(pil)` 11,76 мс | `adapter(pil)` 12,47 мс |
| то же, fp32 | 20,20 мс | 20,05 мс |
| список 64, батч 4 / 16 / 32, img/s | `pipeline(list)` 133,4 / 138,3 / 129,9 | `map` 120,9 / 126,3 / 127,4 |

- Один вызов — 0–0,7 мс, в пределах шума. `map` — 91–98% от ручного `pipeline(list, batch_size=n)`.
- **Решение: проверка типов на границах узлов графа — всегда.** Режима «без проверки» не делаем. Закрывает вопрос «цена проверки типов» из плана графа (12.1–12.2).
- `adapter(path)` дороже `adapter(pil)` на ~3,5 мс — это чтение и декодирование JPEG в `from_raw`, а не накладные расходы.
- **Известная цена — Отложено.** В сценарии «весь список уже на руках» мы медленнее ручного батчинга на 2–9%. Причины: `Image` повторно нормализует готовую PIL-картинку (EXIF, `convert("RGB")` с копией) в `to_thread` на тех же ядрах, что и предобработка HF; пачки `map` неполные (`real batch` 21,3 из 32: 64 элемента → три пачки, валидация не успевает подать входы). Варианты на потом: не копировать картинку, которая уже RGB без EXIF-поворота; класть входы `map` в очередь разом (12.8, «Потом, по замеру»). **Вернуться, когда быстрый путь HF (15.4) ускорит модель:** время валидации не меняется, и её доля вырастет примерно вдвое.

### 15.3. Батчинг: `max_wait_ms=0` — Принято

| fp16, T4 | 1 клиент | 16 клиентов | 64 клиента |
|---|---|---|---|
| без батчинга | 78,7 img/s, 12,6 мс | 79,1, 201 мс | 82,0, 771 мс |
| `max_batch_size=32, max_wait_ms=0` | 78,1, 12,9 мс | **127,2, 125 мс** | **126,2, 505 мс** |
| `max_batch_size=32, max_wait_ms=5` | 55,9, 18,0 мс | 121,5, 131 мс | 124,8, 506 мс |

- **Окно ожидания не нужно.** Пачки растут под нагрузкой сами (12.4): `real batch` 30 из 32 при 64 клиентах и `wait 0`. Одиночный клиент с `wait 5` теряет 5 мс и ~30% пропускной способности, под нагрузкой окно ничего не добавляет.
- **Совет для сервера:** `max_batch_size=16–32, max_wait_ms=0`. Значения по умолчанию (`1`, `0`) не меняем: батчинг включает пользователь.
- **Выигрыш зависит от того, загружает ли модель GPU одна.** fp32 на T4: +14% при 64 клиентах (модель и так на пределе). fp16: +54% пропускной способности и −35% задержки.
- Голый HF pipeline на сервере батчить вызовы разных запросов не умеет: строка «без батчинга» — лучшее, что он даёт (и только если не блокировать event loop прямым вызовом из `async def`).

### 15.4. fp16 и накладные расходы HF pipeline — Открыто

**fp16 — Принято как совет:** `HFAdapter(..., dtype=torch.float16)` через `pipeline_kwargs`, проверено бенчмарком (настройка доходит до pipeline адаптера). Пропускная способность ×2,2–2,4 на T4. Добавить в README раздел «Производительность».

**Время внутри pipeline.** fp16, 64 картинки, батч 32, одна сессия, те же веса и процессор:

| | img/s |
|---|---|
| `pipeline(list, batch_size=32)` | 136,4 |
| свой цикл: процессор → модель → softmax → top-5, предобработка на CPU | 240,7 (×1,76) |
| то же, предобработка на GPU (`processor(..., device=...)`) | 311,1 (×2,28) |

Разбивка на картинку при батче 32 (другая сессия): предобработка PIL 4,8 мс, torchvision CPU 2,0 мс, torchvision GPU 0,9 мс; forward fp32 10,2 мс, fp16 2,5 мс. **~43% времени `pipeline(list)` — механика самого pipeline**, где именно — не выяснено (не нужно, если её обходить).

Варианты:

- **(А) Быстрый `run_batch` внутри `HFAdapter` по задачам — рекомендация.** Модель и процессор по-прежнему загружает `pipeline(...)` (он находит их для любой модели); для HF-задач, у которых есть быстрая реализация, `run_batch` вызывает `pipe.image_processor` и `pipe.model` напрямую, остальные идут через pipeline. Пользователь ничего не меняет.
- **(Б) Отдельный адаптер без pipeline** (`HFModelAdapter`). Чище по разделению, но два HF-адаптера и выбор, который пользователю не нужен.
- **(В) Не трогать** до графа.

Условия для (А), до кода:

- **Совпадение с pipeline.** Классификация не всегда `softmax`: `sigmoid` для `num_labels == 1` и multi-label (`function_to_apply`); учитывать `top_k`. Тест: крошечная ViT, несколько `num_labels`, быстрый путь против pipeline — метки совпадают, score с допуском.
- **Таблица «`hf_task` → быстрая функция батча»** — знание об HF, живёт в HF-адаптере; адаптер перестаёт быть полностью безразличным к задаче. Выход быстрой функции — тот же формат, что у pipeline (`[{"label", "score"}]`): схемы не меняются.
- **Предобработка на GPU — отдельным шагом**, после замера: память GPU, пиксели чуть отличаются от CPU-предобработки. Сначала CPU (×1,76).
- Детекция — после классификации: у процессора есть `post_process_object_detection`, но больше параметров (порог, `target_sizes`).

**torch-адаптер (12.7) быстрее сам по себе не будет:** скорость определяет предобработка пользователя. Он остаётся в плане ради чужих `nn.Module`, а не ради скорости.
