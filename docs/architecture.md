# Архитектура и стиль кода SinglePipe

Документ фиксирует, **как устроены типы и исполнение в SinglePipe и почему**. Если новый код расходится с этими правилами, меняется либо код, либо документ, но осознанно и с записью причины.

Статусы решений:

- **Принято** — действует, новый код пишется так.
- **Цель** — направление согласовано, код ещё не написан или не переведён.
- **Открыто** — решения нет, варианты описаны.

Список задач и их статусы — в `tasks.md`.

## 0. Структура пакета

Статус: **Принято.**

```
singlepipe/
├── __init__.py           # tasks, Task; бэкенды не импортирует
├── tasks.py              # Task, встроенные задачи, get_task
├── adapters/
│   ├── base.py           # Adapter: async, поток модели, батчинг, close
│   └── hf_adapter.py     # HFAdapter (дальше torch, sklearn…)
└── schemas/
    ├── contract.py       # InputSchema, OutputSchema, ensure_implements
    ├── primitives.py     # BBox, Prediction, Detection
    ├── containers.py     # PredictionList
    ├── modalities/       # значения-модальности: Image (дальше Audio, Video…)
    └── image/            # схемы картиночных задач
        ├── base.py       # ImageTaskInput
        ├── classification.py
        └── detection.py
```

*Цель:* `singlepipe/ops/` (операции-клей, раздел 12.8) и `singlepipe/graph/` (раздел 12).

`tests/` повторяет структуру пакета.

## 1. Три вида объектов

Любой класс в библиотеке относится к одному из трёх видов. От вида зависит, от чего наследоваться.

| Вид | Что это | Примеры | Основа |
|---|---|---|---|
| **Запись** | Данные с полями: валидируются, сериализуются, отдаются в FastAPI | `BBox`, `Prediction`, `Detection`, схемы задач | `pydantic.BaseModel` |
| **Значение или контейнер** | Объект со своим поведением, которому от pydantic нужно только одно: лежать в поле модели и валидироваться | `Image`, `PredictionList[T]` | Обычный класс + `__get_pydantic_core_schema__` |
| **Контракт** | Что адаптер требует от схемы задачи | `InputSchema`, `OutputSchema` | `BaseModel` + `abc.ABC` |

**Вопрос-проверка:** «является ли это *записью данных*?» Если да — `BaseModel`. Если это *значение* (картинка, коллекция), то наследование от `BaseModel` принесёт чужой интерфейс (`model_dump`, `copy`, `json`, свой `__iter__`), который будет мешать.

Статус: **Принято.**

### 1.1. Записи — `BaseModel`

- Предсказания и их части неизменяемы: `model_config = ConfigDict(frozen=True)`.
- Методы, которые «меняют» объект, возвращают новый через `type(self)(...)` и аннотируются `-> Self`. Так наследники сохраняют свой тип.
- Поведения в записях минимум: геометрия у `BBox` уместна, логика коллекций — нет (см. 1.2).

### 1.2. Значения и контейнеры — обычный класс

Механизм pydantic v2 для собственных типов — классметод `__get_pydantic_core_schema__`. Класс описывает, как себя валидировать и сериализовать, и после этого используется как тип поля.

Правила:

- Неизменяемость вручную: `__slots__`, без сеттеров; `__eq__`/`__hash__` — если нужны.
- Готовый экземпляр своего типа валидатор пропускает без копирования (`Image`, `PredictionList`). На этом держится передача значений между узлами графа без лишней работы.
- Сериализатор и JSON-схему (для FastAPI) класс определяет сам. `Image` в JSON пишет только размер, а JSON-схема — строка (URL, путь, data URI).
- Ошибка входа — `ValueError` (раздел 5).

**Коллекции** наследуют `collections.abc.Sequence`: реализуются `__getitem__` и `__len__`, а `__iter__`, `__contains__`, `__reversed__`, `index`, `count` приходят бесплатно.

Итерация, `len`, `in`, индексация, `top`, фильтры — поведение **контейнера** (`out.predictions.top(3)`), а не записи-выхода (`out`).

## 2. Контракт схем задач

Статус: **Принято.** Реализован в `schemas/contract.py`; классификация и детекция на нём.

| Класс | Члены |
|---|---|
| `InputSchema[T_co]` | абстрактные `from_raw(cls, raw: object) -> Self` и `to_pipeline_input(self) -> T_co`; свойство `output_context -> Mapping[str, Any]`, по умолчанию `{}` |
| `OutputSchema` | абстрактный `from_pipeline_output(cls, raw: Any, **context: Any) -> Self` |
| `ensure_implements(schema, contract)` | проверка при создании `Task` (раздел 12.6): передан класс, он наследует контракт, абстрактных методов не осталось; иначе `TypeError` с объяснением |

Решения:

- **Контракт наследует `BaseModel` и `abc.ABC`.** Библиотека всегда валидирует данные, поэтому схема без pydantic невозможна, а пользователь наследует одну базу: `class MyInput(InputSchema[str])`. Плата: схему на dataclass или attrs сделать нельзя.
- **Пользовательская схема обязана наследоваться от контракта**, как `nn.Module` в PyTorch или `BaseEstimator` в scikit-learn.
- **Проверка `inspect.isabstract` при создании задачи обязательна.** `@abstractmethod` запрещает только создание объекта; забытый абстрактный *классметод* (`from_raw`) при вызове молча вернёт `None`.
- **`output_context` не абстрактный**, по умолчанию пустой.
- **`__subclasshook__` и виртуальные подклассы не используем.**
- **Схемы поштучные.** Батч собирает адаптер (раздел 12.4); контракт схем от батчинга не меняется.
- **Поля схем — это порты узла графа.** `InputSchema` описывает, что узел читает, `OutputSchema` — что пишет (раздел 12.1).
- **`Any` только на границах с нетипизированным кодом:** сырой ответ бэкенда в `from_pipeline_output` и значения `output_context` (кандидат на `TypedDict` по задачам).

### 2.1. `ImageTaskInput`

Статус: **Принято.** `schemas/image/base.py`.

Общий вход задач с одной картинкой: поле `image: Image`, `from_raw` (готовый экземпляр своего класса проходит как есть, остальное — `model_validate({"image": raw})`, словарь не распаковывается), `to_pipeline_input` → RGB `PIL.Image`. Наследник добавляет только своё (детекция — `output_context` с размерами картинки).

**Сырой вход понимает только схема.** Адаптер вызывает `input_schema.from_raw(raw)` и больше ничего: своих веток для словаря или готовой схемы у него нет. Иначе вход интерпретировали бы два места по-разному.

### 2.2. Вариантность

Правило: **отдаёшь — ковариантно, принимаешь — контравариантно, и то и другое — инвариантно.**

- **`T_co` в `InputSchema` ковариантен**: `InputSchema[Cat]` подходит туда, где ждут `InputSchema[Animal]`.
- **Переопределение подчиняется принципу Лисков:** `from_raw(raw: object)` нельзя сузить до `raw: str`.
- **Только для чтения — абстрактные типы коллекций:** `Mapping` вместо `dict`, `Sequence` вместо `list`.
- **`PredictionList[T_co]` — ковариантный `Sequence`**: одна функция для `PredictionList[Prediction]` принимает предсказания любой задачи.
- **`Callable[[T], bool]` контравариантен по аргументам:** предикат для любого `Prediction` годится для фильтра детекций.

## 3. Сосуществование с pydantic

Статус: **Принято.**

**Нельзя определять в наследниках `BaseModel`:**

- dunder-методы: `__iter__`, `__eq__`, `__hash__`, `__getattr__`, `__copy__`;
- публичные имена: всё с префиксом `model_*`, а также наследие pydantic v1: `copy`, `dict`, `json`, `schema`, `schema_json`, `validate`, `construct`, `parse_obj`, `parse_raw`, `parse_file`, `from_orm`, `update_forward_refs`.

**Страховка:** тест, который падает, если наш атрибут перекрывает атрибут `BaseModel`. *Цель.*

## 4. Примеси

Статус: **Принято** как правило; сейчас не применяются.

Примесь уместна, когда возможности **комбинируются**: у одних задач есть, у других нет. Правила: без полей и состояния; в списке баз перед `BaseModel`; только через публичные атрибуты хозяина; подпадают под запрет имён из раздела 3.

## 5. Ошибки

Статус: **Принято.**

- Любой некорректный вход → `pydantic.ValidationError`.
- Внутри валидаторов бросаем **`ValueError`**, не `TypeError`: pydantic оборачивает только `ValueError` и `AssertionError`.
- Ошибки PIL и файловой системы (`OSError`) превращаются в `ValueError` с указанием источника.
- Сетевые и HTTP-ошибки при загрузке URL остаются исключениями `httpx`.
- Ошибка программиста (не тот класс в `Task`) → `TypeError`.
- Ошибка конфигурации (неизвестное имя задачи, неизвестный HF pipeline) → `ValueError`, **до загрузки модели**, с подсказкой, что делать.
- *Цель:* ошибка внутри графа несёт имя узла и номер элемента при fan-out (раздел 12.2).

## 6. Предсказания

Статус: **Принято.**

- **Иерархия:** база `Prediction` (`label`, `score`, `label_id`); `Detection(Prediction)` + `box: BBox`. Отдельного `Classification` нет: пустой наследник был бы вторым именем для `Prediction`. Общая логика — один раз в `PredictionList[T_co]`. Наследник вроде `DetectionList` заводится, только когда появляется операция, которой нужны коробки (`clip`, `nms`).
- **`score` — вероятность в [0, 1]**, а не логит. Бэкенд, который выдаёт логиты, нормализует их сам.
- **`score` опционален везде.** `score=None` означает «бэкенд не дал уверенности». `top`, `top1`, `filter_by_score` падают с `ValueError`, если хотя бы у одного предсказания скора нет.
- **Сортировка стабильна.**
- **Строка в `filter_by_label` — одна метка.**
- **`BBox.clip`** возвращает `None`, если от коробки внутри картинки ничего не осталось.
- **Схема детекции коробки не обрезает и не отвергает.** Выход — то, что дал бэкенд, даже если коробка чуть за краем (DETR так делает). Обрезка меняет данные и может выкинуть коробку, поэтому это решение пользователя (`BBox.clip`). Зафиксировано тестом.
- **Пустой список предсказаний по умолчанию** у всех выходов (`ImageClassificationOutput()`, `ObjectDetectionOutput()`).

## 7. Когда выносить общее

Статус: **Принято.**

- Выносим только то, что **уже одинаково** минимум в двух реальных задачах (или в двух адаптерах).
- Базовым классам — конкретные имена по смыслу (`ImageTaskInput`, `PredictionList[T]`), а не `BaseInput` «для всех 30 задач».
- Заглушки задач не держим: реализованная задача — это объект `Task`, планы — `tasks.md`. Списка имён «на будущее» в коде нет (раздел 12.6).

## 9. Тесты

Статус: **Принято.**

- Структура `tests/` повторяет структуру пакета. Имена тестовых модулей уникальны по всему дереву.
- **Юнит-тесты** — без моделей, файлов и сети.
- **Интеграционные** — `tests/integration/`. Крошечная модель со случайными весами собирается в тесте; настоящие предобученные модели — `@pytest.mark.slow`.
- **Async-тесты** — через плагин `anyio` (в группе `dev` явно).
- **Конкурентность и батчинг — без замеров времени.** Модель удерживается на `threading.Event`/`Barrier` с таймаутом; неправильная реализация даёт неверные размеры пачек или понятный `TimeoutError`, а не флейк.
- **Проверка самих тестов:** для нового механизма — нарочно сломать реализацию и убедиться, что тесты падают.
- **Импорт пакета** проверяется в отдельном интерпретаторе: в процессе pytest бэкенды уже загружены другими тестами.
- **Сначала тесты, потом рефакторинг.** Перенос в базовые классы не меняет тесты; осознанная смена API (как «коллекции у контейнера») — меняет, и это отмечается в коммите.
- Известный баг — `@pytest.mark.xfail(strict=True, reason=...)`.
- Тест проверяет поведение, а не устройство.

## 12. Исполнение: адаптеры, async, батчинг, граф

Статус раздела: **Цель**, кроме отмеченного «Принято» и «Открыто».

Сценарии, на которых проверялся дизайн: «полка» (детекция → кропы → классификация каждого), номера машин (каскад детекторов), документ → OCR → поля, модерация (независимые ветки), страховой случай (картинки + текст + документ → xgboost). Их целевой код — в `target_api_examples.py`.

### 12.1. Граф — это async-функция

```python
@sp.graph
async def shelf(image: Image) -> Counter[str]:
    dets = await detector(image)
    crops = sp.ops.crop(image, dets.predictions.filter_by_score(0.5))
    results = await sp.each(sku_classifier)(crops)
    return Counter(r.predictions.top1.label for r in results if r.predictions.top1)
```

- **Связи — передача переменных.** Никаких `.add(...)` и строковых ключей: mypy проверяет связи, потому что это настоящие вызовы Python.
- **Порты — поля схем:** `dets.predictions` — это выходной порт детектора.
- **Граф внутри графа — просто вызов.**
- **Функции-клей — обычные функции.** `@sp.node` необязателен: добавляет функцию в протокол прогона и валидирует входы и выходы по аннотациям.
- **Ветки** — `asyncio.TaskGroup` (Python 3.11+).
- **Исполнение «как есть» с записью**, а не трассировка: работает любой Python (`if`, `for`). Трассировка не нужна, потому что батчинг делается на уровне адаптеров (12.4).
- **FastAPI:** декоратор сохраняет сигнатуру (`functools.wraps`), поэтому граф регистрируется как endpoint одной строкой. Проверено: FastAPI видит модели запроса и ответа через обёртку.

### 12.2. Протокол прогона

- Каждый вызов узла записывается: имя, вход, выход, время. Хранится всё (для отладки и настройки); режим «только итог» — когда упрёмся в память.
- Состояние только дополняется, ничего не перезаписывается.
- Протокол живёт в `contextvars`: контекст переходит в задачи `TaskGroup`, поэтому параллельные прогоны (50 запросов к FastAPI) не смешиваются.
- Ошибка несёт имя узла и номер элемента при fan-out: «узел `sku_classifier` [кроп 7 из 14]: …».

### 12.3. Async-ядро и вычисления вне event loop

- Вызов адаптера асинхронный: `await adapter(x)`.
- **Async — это оркестровка; вычисления идут в рабочем потоке модели**, вне event loop. Иначе один forward заморозит весь сервер. torch и C-код отпускают GIL.
- Синхронный фасад для скриптов (`run_sync`) — **Открыто**, не сейчас. В Jupyter `await` работает прямо в ячейке.
- **Реализовано в `Adapter` (`adapters/base.py`) — Принято.** `async def __call__(raw) -> OutT`:
  - `from_raw` — в общем пуле потоков loop'а (`asyncio.to_thread`): валидация может грузить URL и декодировать картинку, и не должна держать ни loop, ни модель;
  - провалидированный вход уходит в очередь своего рабочего потока адаптера (один поток на модель, назван по задаче), вызывающий ждёт `concurrent.futures.Future` через `asyncio.wrap_future`;
  - к event loop адаптер не привязан: очередь живёт в потоке, а не в loop'е, поэтому один адаптер обслуживает вызовы из любого loop'а (в тестах каждый тест — новый loop).
  - Два API (`predict` и `async __call__`) не делаем.
- **Почему не асинхронный `from_raw`:** валидаторы pydantic синхронные, `await` внутри них невозможен. Настоящая async-загрузка URL потребовала бы async-контракта и отдельного слоя загрузки до валидации. `to_thread` даёт тот же результат для loop'а без смены контракта; пересмотреть, если пул потоков станет узким местом.
- **Жизненный цикл — `close()`, Принято.** Досчитывает уже поставленные в очередь вызовы, останавливает поток, вызывает хук `release()` (отпустить модель); повторный вызов безопасен; вызов после закрытия → `RuntimeError`. Постановка в очередь и `close()` упорядочены блокировкой, иначе вызов мог бы проскочить после сигнала остановки и ждать вечно. Поток — демон: без `close()` он не держит интерпретатор. Контекстного менеджера нет: в графе и FastAPI адаптеры живут всё время процесса.
- Модель грузится синхронно в `__init__`, **до** `super().__init__()`: тот запускает поток, и неудачная загрузка не должна оставлять поток.

### 12.4. Батчинг

Статус: **Принято, реализовано в `Adapter`.** Динамический батчинг: пользователь пишет код по одному элементу, пачки собираются сами.

| Уровень | Пример | Механизм |
|---|---|---|
| Внутри одного вызова | `await sp.each(classifier)(crops)` | `sp.each` = `gather`; одновременные вызовы собираются очередью адаптера |
| Табличка | xgboost на 10 000 строк | бэкенд батчевый по природе |
| Между прогонами графа | 50 запросов к FastAPI | та же очередь адаптера |

- **Очередь — в рабочем потоке модели.** Поток берёт первый вызов и добирает следующие, пока не наберёт `max_batch_size` или не истечёт `max_wait_ms` от первого; затем один `run_batch` на всю пачку, результаты — каждому ожидающему. Так работают Triton и `@serve.batch` в Ray Serve.
- **Пачки растут под нагрузкой сами:** вызовы, пришедшие, пока модель считает, попадают в следующую пачку даже при `max_wait_ms=0`. Без нагрузки задержка не добавляется.
- **По умолчанию `max_batch_size=1`, `max_wait_ms=0`** — поведение как без батчинга, пока пользователь не включит. Параметры именованные, одинаковые у всех адаптеров; неверные значения → `ValueError`.
- **Ошибки:**
  - плохой вход отсекается валидацией до очереди и в пачку не попадает;
  - упал `to_pipeline_input` у элемента — падает только он;
  - упал `run_batch` или вернул не то число выходов — падает вся пачка;
  - упал разбор выхода (`from_pipeline_output`) у элемента — падает только он.
  - Рабочий поток от исключения не умирает: иначе все следующие вызовы повисли бы.
- **Отменённый вызов** (таймаут, отмена задачи) выбрасывается из пачки до бэкенда.
- Схемы остаются поштучными; пачка существует только внутри `run_batch`. Склеивать входы в вход своего бэкенда — работа адаптера (список для HF pipeline, 2D-массив для sklearn, `stack` для torch).
- **HF:** пачка уходит как `pipeline(list, batch_size=n)`, один вход — как `pipeline(x)`. Проверено интеграционным тестом на крошечной ViT: один вызов pipeline на 4 картинки, метки и вероятности совпадают с поштучными до 1e-5.
- **Цена:** окно ожидания добавляет задержку каждому запросу ради пропускной способности; `max_batch_size` ограничивает память GPU; у текстов разной длины будет padding (решать с текстовыми задачами).

### 12.5. Устройство и исполнитель

- `device=` — единый параметр у всех адаптеров (`"cpu"`, `"cuda:0"`, `"auto"`).
- **Исполнитель** — отдельная сущность адаптера: «где и как считать». По умолчанию один поток на модель (это же правильно для памяти GPU и потокобезопасности HF pipeline). Позже за тем же интерфейсом: реплики на нескольких устройствах, пул процессов для CPU-моделей с тяжёлым Python-кодом (`spawn`, не `fork`).
- Несколько машин — не наша задача: это ниша Ray и Ray Serve.
- **Открыто:** память GPU при многих моделях (ленивая загрузка, выгрузка на CPU, fp16, квантизация). Сборка Python без GIL (3.14) может сделать поток на модель полноценным параллелизмом и для CPU — проверить готовность бэкендов.

### 12.6. Задача как объект `Task[In, Out]`

Статус: **Принято.** `singlepipe/tasks.py`, `adapters/hf_adapter.py`. Проверено в mypy `--strict` на настоящих схемах.

**Задача определяется входом и выходом.** `Task` связывает имя с двумя схемами и несёт их типы:

```python
@dataclass(frozen=True)
class Task(Generic[InT, OutT]):  # InT: InputSchema[Any], OutT: OutputSchema
    name: str
    input_schema: type[InT]
    output_schema: type[OutT]  # __post_init__: ensure_implements для обеих


image_classification = Task(
    "image-classification", ImageClassificationInput, ImageClassificationOutput
)
object_detection = Task("object-detection", ObjectDetectionInput, ObjectDetectionOutput)
```

- **Встроенные задачи — готовые объекты**, имён схем пользователь не пишет: `HFAdapter(model, sp.tasks.object_detection)`.
- **Своя задача — одна строка, один раз:** `is_cat = Task("is-cat", ImageTaskInput, IsCat)`, дальше передаётся как встроенная. Можно взять готовый вход и свой выход.
- **Схемы проверяются при создании задачи** (`ensure_implements` в `__post_init__`): перепутанные или чужие схемы падают сразу `TypeError`, и у тех, кто mypy не запускает.
- **`Task` — frozen dataclass**, не pydantic-модель: это описание, а не данные.
- **Имена объектов — snake_case** (`image_classification`): это экземпляры, не классы. Не называть объект так, чтобы он перекрыл встроенное имя (`object`); ruff ловит это правилом `A`.
- **Строка для конфигов и CLI — `get_task(name)`**: ищет только среди встроенных задач, неизвестное имя → `ValueError` со списком. Тип выхода по строке — `Task[Any, Any]`.
- **Реестра нет.** Объект задачи и есть связка «задача → схемы».

**Enum имён задач (`TaskType`) удалён.** Причины:

- связку «задача → схемы» несёт `Task`, enum остался бы только списком имён;
- 30 имён при одной-двух реализованных задачах — те же заглушки (раздел 7) и ловушки в автодополнении; `sp.tasks.` показывает ровно то, что работает;
- совпадение значений со строками HF теряет смысл для задач вне HF (OCR, табличка, свои задачи);
- планы живут в `tasks.md`.

**Имя задачи — только имя.** Чем считать задачу, решает адаптер. У встроенных HF-задач имя совпадает со строкой pipeline, и `HFAdapter` берёт его по умолчанию.

**`HFAdapter`:**

```python
HFAdapter(model, task, *, hf_task=None, device=None,
          max_batch_size=1, max_wait_ms=0, **pipeline_kwargs)
```

- `HFAdapter(Adapter[InT, OutT])`, два `@overload`: `Task[InT, OutT]` → точный тип выхода, `str` → `OutputSchema`. `await adapter(raw) -> OutT`, без `cast`.
- `hf_task` — строка HF pipeline; по умолчанию `task.name`. Нужна для своей задачи поверх HF-модели.
- Порядок в `__init__`: разрешить задачу → проверить имя pipeline по реестру HF (`PIPELINE_REGISTRY.check_task`, понимает алиасы и `translation_xx_to_yy`) → проверить torch → загрузить модель → `super().__init__()` (запуск потока).
- Схемы адаптера доступны как `adapter.task.input_schema` / `adapter.task.output_schema`.

### 12.7. Адаптеры: база, бэкенды, Connector

**База `Adapter` — Принято.** `adapters/base.py`, `Adapter(ABC, Generic[InT, OutT])`.

- В базе всё, что от бэкенда не зависит: `async __call__`, валидация вне loop'а, поток модели, очередь и батчинг (12.4), `output_context` каждого входа → его выход, `close()`, ошибки.
- **Бэкенд — один абстрактный метод `run_batch(inputs) -> outputs`:** входы бэкенда (`to_pipeline_input()` каждого) списком, сырые выходы той же длины и в том же порядке. Нарушение длины → `RuntimeError` с именем класса. Вызывается в рабочем потоке, может блокировать.
- **Необязательный хук `release()`** — отпустить модель; вызывается `close()` ровно один раз.
- **`run_batch` публичный: это точка расширения для пользователя.** Свой адаптер под любую библиотеку — подкласс: загрузить модель, `super().__init__(task, ...)`, реализовать `run_batch`. Тип выхода mypy выводит так же, как у `HFAdapter`.
- **Почему вынесено при одном бэкенде** (исключение из раздела 7): выносится не догадка об интерфейсе бэкендов, а механика, которая про HF не знает; интерфейс бэкенда — один метод, и он проверен на бумаге:
  - HF — `pipeline(list, batch_size=n)`;
  - torch — `transform` каждого → `stack` → `model(batch)` → softmax → по строкам;
  - sklearn / xgboost — `vstack` → `predict_proba` → по строкам;
  - адаптер над функцией — функция на пачку или цикл по элементам;
  - remote API — один запрос со списком или цикл запросов.
- **Открыто:** что не ложится в `run_batch` — потоковая генерация текста (выход по токенам) и бэкенды с несколькими входами на элемент. Решать с текстовыми задачами.

**Connector — Цель.**

- `Connector` выбирает адаптер по объекту модели: строка → HF, `nn.Module` → torch, объект с `predict` → sklearn. `backend=` перекрывает автоопределение.
- Connector не импортирует бэкенды: тип проверяется через `sys.modules`, иначе `import singlepipe` потребует torch.
- **Адаптер приводит выход своего бэкенда к формату схемы.** Для HF-задач формат совпадает с выходом pipeline (например `[{"label", "score"}]`); для задач вне HF «сырой выход» определяем мы, и каждый адаптер приводит к нему. Схемы о бэкендах не знают.

**Единые имена параметров — Принято.** Одно понятие — одно имя во всех адаптерах; понятие одного бэкенда называется по нему.

- Общие: `model` (первый позиционный), `task` (второй), `device=`, `max_batch_size=`, `max_wait_ms=`. Всё после `task` — только именованное (`*`).
- Своё у бэкенда: с префиксом или из его терминологии — `hf_task=` у HF, `labels=`/`transform=` у torch.
- Connector пробрасывает именованные параметры в выбранный адаптер; пользователь видит одну форму вызова.

**Адаптер над функцией — Цель.** Пользователь даёт функцию «вход бэкенда → сырой выход», библиотека оборачивает её схемами задачи. Так любая библиотека (ultralytics, OCR-движки, свой код) работает с любой задачей без своего подкласса, и этим же подменяются модели в тестах. На базе `Adapter` это несколько строк: `run_batch` вызывает функцию. Естественное место — рядом с Connector.

**Бэкенды не тянутся без нужды — Принято, реализовано.**

- Ядро (`httpx`, `pillow`, `pydantic`, `numpy`) — всегда. Бэкенды — extras: `hf = transformers + torch`, `detr = hf + timm`, `torch`, `all`. Группа `dev` тянет `singlepipe[all]`.
- **`torch` входит в `hf`:** без него transformers не грузит модели. Нужна своя сборка под CUDA — torch ставится поверх.
- Бэкенд импортируется только в модуле своего адаптера. `singlepipe/__init__.py` экспортирует `tasks` и `Task`, но не адаптеры: `from singlepipe.adapters.hf_adapter import HFAdapter`. Пользователь в целевом API работает через Connector.
- `Image` распознаёт тензоры torch через `sys.modules`, не импортируя torch: тензор не может существовать без уже импортированного torch.
- Без бэкенда — понятная ошибка с командой установки: нет `transformers` → `ModuleNotFoundError` при импорте модуля адаптера; нет `torch` → `ImportError` до загрузки модели. Если `transformers` есть, но сломан, настоящая ошибка не подменяется.
- `import singlepipe`: 3,17 с → 0,20 с. Проверяется тестом в отдельном интерпретаторе.
- Порядок бэкендов: HF → torch → sklearn → remote/ONNX. TF — в конце: Keras 3 работает поверх torch и JAX.

### 12.8. Операции-клей (`sp.ops`)

- Не строим свой язык обработки данных: всё специфичное пользователь пишет обычными функциями.
- Библиотека даёт частые операции, по мере появления в сценариях: `crop`, `to_frame` (координаты кропа → координаты кадра), `reading_order`, `blur`, `score_of`. Сюда же уже существующие `BBox.clip`, `iou`, фильтры `PredictionList`.

## 13. Открытые вопросы

- **Что не ложится в `run_batch`** (потоковая генерация, несколько входов на элемент) — раздел 12.7.
- **Кэш.** Отложен до графа с несколькими моделями. Три разных вещи:
  - одна модель на процесс для нескольких адаптеров (память GPU, 12.5);
  - кэш результатов — обёртка после валидации и до очереди, только для детерминированных задач, ключ включает версию модели; попаданий в инференсе мало, вопросы приватности;
  - **кэш для разработки** (дисковый, по ключу «модель + вход») рядом с протоколом прогона: перезапуск графа после правки клея без пересчёта моделей. Самый ранний кандидат.
  - Мелочь: кэш загрузок по URL.
- **`label_id`.** Поле есть, адаптер его не заполняет. Источник — `pipe.model.config.label2id`. Тест `test_label_id_is_not_filled_yet` фиксирует текущее поведение.
- **`Image` в выходе графа через FastAPI.** В JSON уходит только размер. Если нужна сама картинка (например размытая при модерации) — отдельное решение: data URI, ссылка на хранилище или отдельный endpoint.
- **Синхронный фасад** — раздел 12.3.
- **Память GPU** — раздел 12.5.
- **Имя `PredictionList`** — «пока так», переименовать, если найдётся лучше.
- **Интеграционный тест детекции** на крошечной DETR, по образцу классификации.
- **mypy `strict = false`** в проекте; код пишется и проверяется под `--strict`. Включить `strict` в `pyproject.toml` — отдельное решение.

Закрыто:

- *Python 3.11 и стабы numpy* — решено подъёмом `requires-python` до `>=3.12` (mypy `python_version = 3.12`).
- *`torch` в extra `hf`* — да (12.7).
