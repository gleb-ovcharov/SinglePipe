# SinglePipe — контекст проекта

## Что это

SinglePipe — Python-библиотека: типизированный асинхронный оркестратор инференса многих ML-моделей поверх разных бэкендов. Не переизобретаем HuggingFace, sklearn или torch — оборачиваем их в единый API с pydantic-схемами на входе и выходе и связываем модели в графы.

**Позиционирование одной фразой:** «типизированный оркестратор мультимодельных инференс-пайплайнов поверх любых бэкендов — HF, torch, sklearn, ONNX, remote API».

**Ниша:** между LangChain (только LLM) и Ray Serve (только прод-инфраструктура). Ключевое отличие — честная мультимодальность: CV, текст, аудио и **табличные модели** (sklearn, xgboost, lightgbm) в одном графе. Типовая форма графа: «найти → вырезать → распознать → собрать → решить», где решение часто принимает табличная модель по признакам от остальных. С vLLM по скорости не соревнуемся.

**Опубликовано на PyPI как `singlepipe` (v0.0.1, резерв имени).** Автор — GlebOv. SinglePipe также тема дипломной работы Глеба. Демо-сценарий для диплома — «страховой случай»: фото повреждений + текст заявления + документ → xgboost.

**Документы проекта:**
- `claude/architecture.md` (копия: `docs/architecture.md`) — источник истины по типам, контракту, исполнению (async, батчинг, граф), ошибкам, тестам и стилю кода. Перед любым архитектурным обсуждением — прочитать.
- `claude/tasks.md` (копия: `docs/tasks.md`) — все задачи `TaskType` и их статусы. Память о нереализованных задачах живёт здесь, заглушек в коде нет.
- `target_api_examples.py` — целевой код пользователя для 8 сценариев (сейчас в синхронном виде; переписать под async на шаге 1 плана).

## Архитектурные принципы

1. **Не переизобретаем нижние слои.** Бэкенд делает препроцесс/forward/постпроцесс. Наш вклад — типизированная граница, связывание моделей и исполнение.
2. **Схемы pydantic — это контракт.** Вход валидируется и нормализуется (картинки — PIL RGB), выход — типизированный объект. **Библиотека всегда валидирует данные.**
3. **Три вида объектов** (architecture.md, раздел 1): **записи** → `BaseModel` (`BBox`, `Prediction`, `Detection`, схемы задач); **значения и контейнеры** → обычный класс + `__get_pydantic_core_schema__` (`Image`, `PredictionList`); **контракт** → `InputSchema`/`OutputSchema` (`BaseModel` + `ABC`).
4. **Контракт схем** (`schemas/contract.py`): `InputSchema[T_co]` — `from_raw(cls, raw: object) -> Self`, `to_pipeline_input() -> T_co`, `output_context -> Mapping[str, Any]` (по умолчанию `{}`). `OutputSchema` — `from_pipeline_output(cls, raw: Any, **context) -> Self`. `ensure_implements` проверяет класс, наследование и `inspect.isabstract`. Схемы поштучные; поля схем — порты узла графа.
5. **Граф — это async-функция** (`@sp.graph async def`). Связи — переменные, порты — поля схем, ветки — `TaskGroup`, fan-out — `sp.each`. Исполнение «как есть» с записью протокола в `contextvars`, без трассировки. Граф = FastAPI-endpoint одной строкой.
6. **Async — оркестровка, вычисления — в рабочем потоке модели**, вне event loop.
7. **Батчинг — забота адаптера**: очередь с `max_batch_size`/`max_wait_ms`, по умолчанию батч 1. Одновременные `await` собираются в пачку. Контракт схем от этого не меняется.
8. **Устройство и исполнитель — параметры адаптера.** По умолчанию один поток на модель; реплики и процессы — позже за тем же интерфейсом. Несколько машин — не наше (Ray).
9. **Адаптер приводит выход своего бэкенда к формату схемы.** Схемы о бэкендах не знают. `Connector` выбирает адаптер по объекту модели, не импортируя бэкенды.
10. **Не перекрывать имена `BaseModel`.** Коллекционное поведение — у контейнера (`out.predictions.top(3)`), не у записи.
11. **Вариантность:** отдаёшь — ковариантно, принимаешь — контравариантно. `object` в `from_raw` нельзя сузить. Только для чтения — `Mapping`/`Sequence`.
12. **Ошибки:** плохой вход → `ValidationError` (в валидаторах `ValueError`; PIL/OS → `ValueError`). Сеть → `httpx`. Ошибка программиста → `TypeError`. В графе — имя узла и номер элемента.
13. **Предсказания:** `score` — вероятность в [0, 1], опционален везде; `None` → `top`, `top1`, `filter_by_score` падают. Сортировка стабильная. Строка в `filter_by_label` — одна метка.
14. **Postel's law** и **иммутабельность** (`frozen=True`, `__slots__`, `type(self)(...)` + `-> Self`).
15. **Выносим общее, когда оно уже одинаково минимум в двух реальных местах** (задачах, адаптерах).
16. **Не оптимизируем заранее** (кэш, реплики, процессы, память GPU — по измеренной проблеме). **Исключение:** async-ядро и батч-контракт адаптера закладываются сразу — потом их не встроить без переписывания.
17. **Не строим свой язык обработки данных.** Клей — обычные функции; `sp.ops` даёт только частые операции (`crop`, `to_frame`…).
18. **Enum-член ≠ реализованная задача.** `TaskType` — семантика, `tasks.md` — планы, реестр — рантайм-истина.

## Что уже сделано

- **Структура:** `singlepipe/tasks.py` (`TaskType`), `adapters/hf_adapter.py`, `schemas/{contract,primitives,containers,registry}.py`, `schemas/modalities/image.py`, `schemas/image/{base,classification,detection}.py`. Заглушки задач удалены.

- **Основы:** `InputSchema`/`OutputSchema`/`ensure_implements`; `BBox` (`iou`, `clip` → `None`), `Prediction`, `Detection`; `Image`; `PredictionList[T_co: Prediction]`; `ImageTaskInput`.
- **Классификация на основах:** `ImageClassificationInput(ImageTaskInput)`, `ImageClassificationOutput(OutputSchema)` с `predictions: PredictionList[Prediction]`. Интеграционные тесты (крошечная ViT и `google/vit-base-patch16-224` под `slow`) зелёные.
- **Детекция — старая форма**, тестов нет (план, шаг 3).
- **`HFAdapter(model_name, task, device=None, **pipeline_kwargs)`** — синхронный, тип выхода теряется (план, шаги 1–2).
- **Тесты:** 219 зелёных. Async-тесты — через уже установленный плагин `anyio`.
- **mypy сломан** (план, шаг 0). Запускать через `uv run mypy`.
