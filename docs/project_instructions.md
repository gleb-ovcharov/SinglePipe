# SinglePipe — контекст проекта

## Что это

SinglePipe — Python-библиотека: типизированный асинхронный оркестратор инференса многих ML-моделей поверх разных бэкендов. Не переизобретаем HuggingFace, sklearn или torch — оборачиваем их в единый API с pydantic-схемами на входе и выходе и связываем модели в графы.

**Позиционирование одной фразой:** «типизированный оркестратор мультимодельных инференс-пайплайнов поверх любых бэкендов — HF, torch, sklearn, ONNX, remote API».

**Ниша:** между LangChain (только LLM) и Ray Serve (только прод-инфраструктура). Ключевое отличие — честная мультимодальность: CV, текст, аудио и **табличные модели** (sklearn, xgboost, lightgbm) в одном графе. Типовая форма графа: «найти → вырезать → распознать → собрать → решить», где решение часто принимает табличная модель по признакам от остальных. С vLLM по скорости не соревнуемся.

**Опубликовано на PyPI как `singlepipe` (v0.0.1, резерв имени).** Автор — GlebOv. SinglePipe также тема дипломной работы Глеба. Демо-сценарий для диплома — «страховой случай»: фото повреждений + текст заявления + документ → xgboost.

**Документы проекта:**
- `claude/architecture.md` (копия: `docs/architecture.md`) — источник истины по типам, контракту, исполнению (async, батчинг, граф), ошибкам, тестам и стилю кода. Перед любым архитектурным обсуждением — прочитать.
- `claude/tasks.md` (копия: `docs/tasks.md`) — все задачи, реализованные и планируемые, и их статусы. Память о нереализованных задачах живёт здесь: ни заглушек, ни enum имён в коде нет.
- `target_api_examples.py` — целевой код пользователя для 8 сценариев (сейчас в синхронном виде и с устаревшей формой `task=`; переписать под async и `Task`, план, шаг 1).

## Автор и стиль общения

Разработчик — Глеб. Linux (Ubuntu 26.04, Python 3.14 локально), менеджер зависимостей `uv`. `requires-python = ">=3.12"`. mypy в проекте `strict = false`, но код пишется и проверяется под `--strict`. Прочитал «Fluent Python» (2-е изд.) — опирается на неё, но в типизации и метапрограммировании ещё учится.

**Как он хочет общаться:**
- По-русски, без расшаркиваний и «отличный вопрос!».
- Прямо, честно, с признанием проблем в его коде.
- Пошагово: сначала обсудить решения, потом код.
- **Код писать только когда он явно просит.** Когда устал, просит «исправь», «погнали» или матерится — писать код, не переспрашивать.
- Признавать, когда идея хорошая (и когда его идея лучше моей), и честно говорить, когда преждевременная.
- Не бояться сказать «стоп, ты уверен» перед необратимым действием.
- Когда он спрашивает «что это за синтаксис» / «разбери подробно» — объяснять по частям, с примерами из нашего кода, с проверкой в интерпретаторе.

**Что он не любит:**
- Оверинжиниринг и абстракции без реальной потребности.
- «Красивые» API поверх несуществующей машины.
- Магию, которую нельзя объяснить.
- Давление принципами вместо ответа на вопрос.
- **Затянутое проектирование.** Хочет двигаться: абстракции доводить, когда в них упрётся реальная задача, а не заранее. Но архитектурные развилки, которые дорого менять потом (async, батч-контракт, форма графа), обсуждать сразу.
- Многословные `.add(...).add(...)`-построители и строковые ключи вместо кода.
- **Когда я забегаю вперёд:** лезу в файлы, которые он не просил трогать, или пишу код до того, как договорились о плане. Делать ровно тот шаг, о котором договорились.
- **Когда вываливаю несколько файлов сразу.** Код — по одному файлу: показал, объяснил, он решил, потом следующий. Выбор варианта в обсуждении — это решение, а не разрешение писать код. Исключение — когда он сам прислал несколько файлов на правку.

**Что он ценит:**
- Когда я замечаю мелочи до того, как они станут багами.
- Объяснение компромиссов, а не «правильный ответ» — решает он.
- Утверждения, проверенные в интерпретаторе или mypy, а не по памяти.
- Примеры целевого кода пользователя, чтобы посмотреть на API со стороны.

**Стиль его кода** (подробно — `architecture.md`, раздел 10): докстринги на английском, у модуля docstring «почему», `from __future__ import annotations`, разделы через `# ---------------- раздел`, тесты классами `TestX` с `pytest.param(..., id=...)`, `from_raw` через `cls.model_validate({...})`. Перед тем как писать файл — смотреть на его существующий код и повторять стиль.

## Архитектурные принципы

1. **Не переизобретаем нижние слои.** Бэкенд делает препроцесс/forward/постпроцесс. Наш вклад — типизированная граница, связывание моделей и исполнение.
2. **Схемы pydantic — это контракт.** Вход валидируется и нормализуется (картинки — PIL RGB), выход — типизированный объект. **Библиотека всегда валидирует данные.**
3. **Три вида объектов** (architecture.md, раздел 1): **записи** → `BaseModel` (`BBox`, `Prediction`, `Detection`, схемы задач); **значения и контейнеры** → обычный класс + `__get_pydantic_core_schema__` (`Image`, `PredictionList`); **контракт** → `InputSchema`/`OutputSchema` (`BaseModel` + `ABC`).
4. **Контракт схем** (`schemas/contract.py`): `InputSchema[T_co]` — `from_raw(cls, raw: object) -> Self`, `to_pipeline_input() -> T_co`, `output_context -> Mapping[str, Any]` (по умолчанию `{}`). `OutputSchema` — `from_pipeline_output(cls, raw: Any, **context) -> Self`. `ensure_implements` проверяет класс, наследование и `inspect.isabstract`. Схемы поштучные; поля схем — порты узла графа. Сырой вход понимает только схема (`from_raw`), адаптер его не разбирает.
4a. **Задача — объект `Task[In, Out]`** (`tasks.py`, architecture.md 12.6): имя + две схемы, проверка схем в `__post_init__`. Встроенные задачи — готовые объекты (`sp.tasks.image_classification`), своя задача — одна строка `Task("is-cat", In, Out)`. Строки из конфигов — `get_task(name)`. Имя — только имя; чем считать, решает адаптер. Enum имён и реестра нет.
5. **Граф — это async-функция** (`@sp.graph async def`). Связи — переменные, порты — поля схем, ветки — `TaskGroup`, fan-out — `sp.each`. Исполнение «как есть» с записью протокола в `contextvars`, без трассировки. Граф = FastAPI-endpoint одной строкой.
6. **Async — оркестровка, вычисления — в рабочем потоке модели**, вне event loop.
7. **Батчинг — забота адаптера** (динамический): очередь в рабочем потоке модели, `max_batch_size`/`max_wait_ms`, по умолчанию батч 1 без ожидания. Одновременные `await` собираются в пачку; под нагрузкой пачки растут сами. Схемы остаются поштучными.
7a. **База `Adapter`** (`adapters/base.py`): вся механика (async, поток, батчинг, `close`) в базе, бэкенд реализует один метод `run_batch(inputs) -> outputs`, хук `release()`. Это и точка расширения для пользователя: свой адаптер под любую библиотеку. Модель грузится **до** `super().__init__()`.
8. **Устройство и исполнитель — параметры адаптера.** По умолчанию один поток на модель; реплики и процессы — позже за тем же интерфейсом. Несколько машин — не наше (Ray).
9. **Адаптер приводит выход своего бэкенда к формату схемы.** Схемы о бэкендах не знают. `Connector` выбирает адаптер по объекту модели, не импортируя бэкенды. **Единые имена у всех адаптеров:** `Adapter(model, task, *, device=..., max_batch_size=..., max_wait_ms=..., <параметры бэкенда с его префиксом>)`, например `hf_task=`. **Бэкенды — extras** (`singlepipe[hf]` = transformers + torch, `[detr]`, `[torch]`, `[all]`); `import singlepipe` бэкенд не тянет, адаптеры импортируются из своих модулей.
10. **Не перекрывать имена `BaseModel`.** Коллекционное поведение — у контейнера (`out.predictions.top(3)`), не у записи.
11. **Вариантность:** отдаёшь — ковариантно, принимаешь — контравариантно. `object` в `from_raw` нельзя сузить. Только для чтения — `Mapping`/`Sequence`.
12. **Ошибки:** плохой вход → `ValidationError` (в валидаторах `ValueError`; PIL/OS → `ValueError`). Сеть → `httpx`. Ошибка программиста → `TypeError`. В графе — имя узла и номер элемента.
13. **Предсказания:** `score` — вероятность в [0, 1], опционален везде; `None` → `top`, `top1`, `filter_by_score` падают. Сортировка стабильная. Строка в `filter_by_label` — одна метка.
14. **Postel's law** и **иммутабельность** (`frozen=True`, `__slots__`, `type(self)(...)` + `-> Self`).
15. **Выносим общее, когда оно уже одинаково минимум в двух реальных местах** (задачах, адаптерах). Исключение — механика, которая заведомо не зависит от варианта (так вынесен `Adapter` при одном бэкенде).
16. **Не оптимизируем заранее** (кэш, реплики, процессы, память GPU — по измеренной проблеме). **Исключение:** async-ядро и батч-контракт адаптера — заложены. Кэш — когда появится граф с несколькими моделями (первым — кэш для разработки).
17. **Не строим свой язык обработки данных.** Клей — обычные функции; `sp.ops` даёт только частые операции (`crop`, `to_frame`…).
18. **Реализованная задача — это объект `Task`.** Планы — только в `tasks.md`, списков имён «на будущее» в коде не держим.

## Что уже сделано

- **Структура:** `singlepipe/__init__.py` (`tasks`, `Task`), `tasks.py` (`Task`, встроенные задачи, `get_task`), `adapters/{base,hf_adapter}.py`, `schemas/{contract,primitives,containers}.py`, `schemas/modalities/image.py`, `schemas/image/{base,classification,detection}.py`. Заглушки, enum `TaskType` и реестр удалены.
- **Основы:** `InputSchema`/`OutputSchema`/`ensure_implements`; `BBox` (`iou`, `clip` → `None`), `Prediction`, `Detection`; `Image` (тензоры torch через `sys.modules`, без импорта torch); `PredictionList[T_co: Prediction]`; `ImageTaskInput`.
- **Задачи:** `image_classification`, `object_detection` — объекты `Task`.
- **Классификация на основах.** Интеграционные тесты: крошечная ViT, `google/vit-base-patch16-224` под `slow`, своя задача поверх HF через `hf_task`, батч из 4 через настоящий pipeline.
- **Детекция на основах:** `ObjectDetectionInput(ImageTaskInput)` + `output_context` с размерами, `ObjectDetectionOutput` с `PredictionList[Detection]`. Коробки за краем не обрезаются и не отвергаются. Юнит-тесты есть, интеграционного (крошечная DETR) нет.
- **`Adapter`** — база: `await adapter(x)`, валидация в общем пуле потоков, очередь в рабочем потоке модели, динамический батчинг, `close()`/`release()`. Бэкенд — `run_batch`.
- **`HFAdapter(model, task, *, hf_task=None, device=None, max_batch_size=1, max_wait_ms=0, **pipeline_kwargs)`** — тип выхода виден mypy без `cast`; pipeline и torch проверяются до загрузки модели; понятные ошибки без extras.
- **Зависимости:** ядро — httpx, pillow, pydantic, numpy; бэкенды — extras. `import singlepipe` — 0,2 с (было 3,2 с).
- **Тесты:** 304 зелёных, `uv run mypy singlepipe tests` зелёный. Async — плагин `anyio` (в `dev` явно). Конкурентность и батчинг — через `Event`/`Barrier`, без замеров времени. mypy запускать через `uv run`.

## Правила работы

- По-русски. Уточнять, если у решения несколько защитимых вариантов.
- Код — только по явной просьбе; если пишем — полностью и работоспособно, с тестами, прогнанными ruff/pytest/mypy. Без доступа к его репозиторию — воспроизводить его модули по присланным файлам и проверять на них, а не на догадках.
